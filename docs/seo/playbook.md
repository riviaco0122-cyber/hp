# SEO / AIO 手順書（全部署共通の判断基準）

> **基本姿勢**: 読み手にとって価値のある情報を、高いクオリティで届ける。SEO/AIO はその結果として付いてくる。基準を満たすために文字数や見出しを水増ししない。情報の濃さは保ち、文字量は図解・表・折りたたみでスッキリ見せる（人の方針 2026-10-12）。

アキヤドの目的は「空き家オーナー・宿の開業検討者・観光事業者が検索する悩みに答え、サービスページとお問い合わせへつなげる」こと（`docs/site-spec.md` 5-2）。アクセス数そのものではなく、**相談につながる読者を増やすこと**を優先する。

目次: 1 キーワード ／ 2 記事の構成 ／ 3 AIO ／ 4 テクニカルSEO ／ 5 品質の採点（100点・90点合格） ／ 6 人の確認が必要なもの ／ 7 法務・炎上リスク ／ 8 誤りが見つかったとき ／ 9 既存記事の見直し

## 1. キーワードの選び方（企画・マーケ部）

- RIVIA のサービス（空き家再生／開業・運営支援／不動産協業／WEB集客／WEB採用）につながる悩みに限る。
- 優先順位: ①Search Console で順位5〜20位・表示が多いもの（既存記事の改善） ②既存記事と重ならない新しい悩み ③季節・制度改正などの時事。
- 1記事＝1つの検索意図。既存記事と意図が重なるなら新記事を作らず既存記事を強化する（共食い＝カニバリゼーションを避ける）。Search Console で同じキーワードに2本以上の記事が出ていたら、統合か役割分担を提案する。
- 検索意図の型（知りたい／比べたい／やり方を知りたい／依頼先を探したい）を構成案に書き、型に合った形（定義・比較表・手順・チェックリスト）にする。
- `docs/seo/keywords.md` に候補・担当記事・状態を記録する。
- **新規記事は週2本まで**（似た記事の量産と、Google のスパムポリシー「大量生成コンテンツの不正使用」を避けるため）。超える場合は人の確認が必要。

**記事の建て付けは、特定の地域に縛らない（人の方針 2026-10-12）。** 事業は静岡に限らない（広島県竹原市でも開業予定。ただし、記事に載せてよいかは人の確認が要る）。記事は「全国どこでも当てはまる判断・手順」を主役にして、静岡県などの地域の数字・制度は**「例」**として使う（title・見出しにも「静岡県の例」と書き分ける）。静岡県だけの調査結果を主役にした記事は、読み手が静岡県に関わる人に絞られてしまう。ほかの地域（広島県、全国）の公的な数字・制度を、公式ページの本文で確認できる範囲で、例として足してよい。

## 2. 記事の構成（企画・マーケ部の構成案・執筆担当）

`docs/site-spec.md`「記事ページの構成（SEO・AIO対策）」に従う。要点:

1. タイトル: 主キーワードを前半（20字以内）に。サフィックスを除いて **40文字以内**。
2. meta description: リード文と同じ要約。**50〜140文字**。
3. **この記事のポイント**: 結論を3〜5行で先に示す（AIに要約・引用されやすい）。
4. 見出し h2 は **4〜8個**。60%以上を「疑問文」か「結論」の形にする。各見出しの直後の1〜2文で、その問いに答えきる。
5. 1文は平均60字以下。80字を超える文は全体の5%以下。
6. 数値・制度には必ず出典（資料名・公表年）を付ける。出典のない数値は書かない。
7. よくある質問（3問以上）＋構造化データ FAQPage（本文と一致）。
8. 参考資料（3件以上・公的機関か、集計データを公表している観光系大手企業〈JTB・HIS など〉を含む）、公開日時点の情報である旨の注記、執筆者・監修者情報、関連サービスへのリンクと相談ボタン。
9. 内部リンク: 本文から関連する記事へ2本以上、関連サービスへ1本以上。読者の状況別ガイド（売りたい／活かしたい／副業）のどれに入るかを構成案で決める。

### 2-1. 読みやすさの基準（スマホ 390px で読む人向け。企画・執筆・エンジニア・品質管理の全員が守る）

読者の多くはスマホで読む。文字が詰まった記事は、正しくても読まれない。次を満たす。

1. **1段落は2〜3文以内**（目安150字以内）。長くなったら段落を分ける。
2. **見出しの直後は、結論の1文**。その1文は自動で太字になる（節の最初の段落の一文目）。補足は2文目以降に回す。
3. **「この記事のポイント」は1項目を短く**（要点の一文は40字以内）。補足があるときは「要点。補足。」の2文にすると、補足が小さく淡く表示される。長い注記は本文に回す。
4. **長い計算式は本文に並べない**。数値の比較は表にし、式は `<details class="fold"><summary>表の計算式を見る</summary><ul>…</ul></details>` で折りたたむ（式だけの箇条書き `<ul>` は自動で「式」の枠になる）。同じ式を何度も書かない。
5. 注意書きは `<div class="callout callout--note"><p class="callout__label">注意</p><p>…</p></div>`、節の結論を目立たせたいときは `callout callout--answer` を使う（1記事に2つまで）。
6. 表は列を4つ以内にし、先頭列を項目名にする。セルに長文を入れない。
7. **スマホで1画面（約700px）に、文字だけの塊が続かない**ようにする。目安は、段落・箇条書き・表・図のどれかが1画面に2種類以上入ること。
8. 目次は自動で折りたたまれる。見出しは短く、1行に収まる語を前に置く。
9. **スマホ1画面（約700字相当）に文章だけが続かない。3〜4画面に1回は、図・表・カード・数字ハイライトのどれかを入れる。比較・手順・数値の並びは、文章でなく部品で見せる**（カルーセルカード・要点ボックス・比較カード・数字ハイライト。書き方は `docs/seo/components.md`）。情報の濃さは保ち、文字量だけをスッキリ見せる。
10. 一覧（ガイド・学ぶ・記事一覧）に載る長い title は、記事データの `short`（表示名・〜22字）と `blurb`（補足・〜18字・省略可）で短く見せる。SEO 用の title は変えない。

## 3. AIO（AIによる検索回答）で引用されるための基準

- 定義文を1文で言い切る（「◯◯とは、△△のことです。」）。
- 比較は表、手順は番号付きリストにする。数値は「数値＋単位＋時点＋出典」をそろえて書く（例: 「約3,687万人（2024年、日本政府観光局）」）。
- 一次情報を入れる: RIVIA が実際に宿を運営して得た気づき・数値（`docs/brand/experience.md` にあるものだけを使う。作り話は禁止）。
- 他者の一次情報は、**チャンネル・アカウントとして公に発信している運営者の発言だけ**を、出典（発信者名・URL）を明記して要約で紹介する。事実の部分は公的資料で裏を取る。視聴者コメント・一般の人の投稿は「読者の悩みの発見」にだけ使い、記事に引用・要約しない。集め方と扱い方は `docs/sources/README.md`。
- 各 h2 の節は、**その節だけ読んでも意味が通る**ように書く（AI は段落単位で抜き出して引用するため）。「上記」「前述の」を使わず、主語と固有名詞を繰り返す。
- 著者・監修者・運営会社の情報（E-E-A-T）を明示する。会社名・サービス名の表記は `docs/brand/glossary.md` の正式表記で統一する（AI が同じ会社として認識しやすくなる）。
- `llms.txt` でサイトの構成と主要記事を AI に案内する（毎日 `tools/build.py` で作り直す）。
- 構造化データの Organization は、全ページで同じ名称・所在地・URL を使う（追加・変更はエンジニア部が行い、人の確認）。
- AI クローラ（GPTBot・Google-Extended など）に記事を読ませるかどうかは `seo/robots.txt` で人が決める。いまはすべて許可。変更は人の確認。
- 記事の更新日（dateModified）は、内容を実際に直したときだけ変える。誤字の修正だけで更新日を新しくしない。

## 4. テクニカルSEO（エンジニア部）

`python3 tools/seo_check.py` のエラーと、`node tools/check/site_check.js`（サイト全体の点検）の重大は必ず 0 にする。HTML は直接書き換えず、`tools/build.py` で作り直す。主なチェック項目:

- title／meta description の有無・長さ・重複、canonical、OGP
- h1 が1つ、画像の alt、内部リンク切れ
- 構造化データ（Article／FAQPage／BreadcrumbList／CollectionPage）の書式と日付の整合
- sitemap.xml の網羅性と lastmod、noindex のページが sitemap にないこと
- 日本語版と英語版の hreflang の対応
- 表示速度: カードの画像は `images/photos/w/` の WebP 軽量版（幅800）を使う。写真は原寸のまま格納し再圧縮しない（site-spec の方針）。新しい写真を足すときは、権利（自社撮影・ライセンス）を確認する（7章）。
- **画像**: 新しい写真は、人が `images/photos/` に入れたもの（自社撮影、または利用許諾を確認した素材）だけを使う。AI 生成画像・出所が分からない画像は使わない。記事の構造化データの image は、記事トップの写真にする。
- 既知の課題: 予約公開の記事は公開日前でも HTML と sitemap に載っている（`js/main.js` で画面上だけ隠している）。方式の見直しは `docs/seo/calendar.md` で管理。

## 5. 品質の採点基準（品質管理部）— 100点満点・90点以上で合格

### 5-1. 必須条件（ゲート）
次のどれか1つでも当てはまれば、**点数に関係なく不合格**。

| ゲート | 確認方法 |
|---|---|
| 事実の誤りが1件でもある | 品質管理部が出典と照合 |
| 出典を確認できない数値・制度の記述が1件でもある | 同上 |
| 重大な NG 表現（誇大・保証・断定）がある | `tools/article_score.py`（終了コード 2） |
| 7章の法務・炎上リスクに1件でも当てはまる | 品質管理部が7章のチェックリストで確認 |
| `docs/brand/experience.md` にない RIVIA の体験・実績を書いている | 品質管理部が照合 |
| `tools/seo_check.py` のエラー、または `tools/check/site_check.js` の重大が1件以上（作り直しの後） | 両ツール |
| 既存記事と主キーワード、または読者の疑問の過半が重なる（共食い・量産） | 品質管理部が `keywords.md` と既存記事の title・h2 を照合 |

**ゲートの対象と、出典の求め方（人の方針 2026-10-12）**
- ゲートの対象は **数値・制度・法律・税・固有名詞などの「事実」の主張**だけ。**見解・感想・一般論・考え方・体験の解釈は、事実と区別して書けば出典は不要**（「〜と考えます」「〜という見方があります」「一般には〜」「私たちは〜と感じました」など、事実でないと読み手に分かる書き方にする）。公的機関の情報になくてもよい。
- 出典の求め方は **発行元・資料名・年（あれば URL）を書くところまで**。出典の**証跡の保証**（本文を開いての照合、スクリーンショットや保存、複数の出典での裏取り）までは求めない。検索で確認でき、書いた出典と食い違わなければ足りる（確認できなかった数値は書かない）。
- 事実と見解が混ざる文は分ける。迷ったら、数字や制度の部分だけに出典を付け、評価の部分は見解として書く。

### 5-2. 機械採点（40点）— `python3 tools/article_score.py <原稿 or HTML>`
| 項目 | 満点 | 満点の条件 |
|---|---|---|
| title の長さ | 2 | 40字以内 |
| 主キーワードの位置 | 3 | title の前半20字以内 |
| meta description | 3 | 50〜140字 |
| この記事のポイント | 4 | 3〜5項目 |
| 見出し h2 の数 | 2 | 4〜8個 |
| 見出しの形 | 2 | 60%以上が疑問・結論の形 |
| よくある質問 | 4 | 3問以上、構造化データと一致 |
| 参考資料 | 5 | 3件以上、公的機関か観光系大手企業（JTB・HIS など）の集計データを含む |
| 他の記事へのリンク | 2 | 本文から2本以上 |
| サービスへのリンク | 2 | 1本以上 |
| 1文の平均 | 2 | 60字以下 |
| 長い文の割合 | 2 | 80字超が5%以下 |
| 軽微な NG 表現 | 4 | 0件（1件ごとに -2） |
| 表記ゆれ | 3 | 0件（1件ごとに -1） |

引用（かぎかっこ・引用ブロック）の中の表記は減点しない。**点数のために引用やレビューの原文を書き換えることは捏造としてゲート違反。**

### 5-3. 品質管理部の採点（60点）— 減点方式で、根拠を必ず書く
| 項目 | 満点 | 減点のルール |
|---|---|---|
| 正確性 | 20 | 数値・制度を1つずつ出典と照合する。表現が出典より強い（断定しすぎ）1か所 -3、時点・年度の書き漏れ1か所 -2、出典の資料名があいまい1か所 -1。（誤り・出典なしはゲートで不合格） |
| 検索意図への回答 | 10 | 構成案の「読者の疑問」のうち、答えていないもの1つ -3。見出しの直後で答えきっていない見出し1つ -1 |
| 独自性・一次情報 | 10 | RIVIA の一次情報（experience.md）または出典つきの他者の一次情報が **0件なら最大4点**。上位記事にない視点・情報が1つもなければ -3。他サイトの言い換えに見える節1つ -2 |
| ブランド準拠 | 5 | voice.md の文体ルール違反1か所 -1（呼びかけの「あなた」、感嘆符、くだけた表現など） |
| 読みやすさ・構成 | 5 | 比較なのに表がない・手順なのに番号付きリストがない 1か所 -1、段落が長すぎて読みにくい節1つ -1、スマホ1画面（約700字相当）に文章だけが3〜4画面続く箇所 1か所 -1（部品の使い方は components.md） |
| 導線 | 5 | サービスへの誘導が唐突・押し付けがましい -2、ガイド（売りたい／活かしたい／副業）への位置づけがない -1、相談ボタンにつながる流れがない -2 |
| 法務・炎上リスクの配慮 | 5 | 7章のチェックリストで、ゲートには当たらないが配慮が足りない点1つ -1（例: 「〜の場合があります」が抜けている、専門家への確認の案内がない） |

### 5-3b. 価値の基準は E-E-A-T（人の方針 2026-10-12）
「読み手にとって価値のある記事」の基準は、Google の品質評価の考え方 **E-E-A-T**（Experience 経験・Expertise 専門性・Authoritativeness 権威性・Trustworthiness 信頼性）に置く（順位を直接決める指標ではなく、価値ある記事かを測る物差し。AIO で引用されやすい条件とも重なる）。採点の100点は変えず、**品質管理部は5-3 の各項目がどの E-E-A-T にあたるかを意識して採点し、採点表の末尾に「E-E-A-T の判定」を必ず書く**（厳しくしすぎず、毎日1本出せる水準を保つ）。

| 観点 | 見ること | 主に反映される採点項目 |
|---|---|---|
| Experience（経験） | RIVIA の実体験（experience.md の確認済みの節）や、運営者の発信など、実際にやった人にしか書けない情報があるか。体験の捏造がないか | 独自性・一次情報 |
| Expertise（専門性） | 制度・数字・手順が正確で、読み手が自分で判断できる深さがあるか。上位記事にない切り口・整理があるか | 正確性、検索意図への回答、独自性 |
| Authoritativeness（権威性） | 公的機関・統計・一次資料を出典に挙げているか。著者・監修者・運営会社の情報があるか | 機械採点（参考資料）、正確性 |
| Trustworthiness（信頼性） | 事実誤り・断定しすぎ・古い情報がないか。広告・自社サービスの案内が誠実か（読み手の利益を損なわないか）。専門家への確認の案内があるか | 正確性、法務・炎上リスク、導線、ゲート |

- **差し戻しにするのは、Trustworthiness が「なし」（事実誤り・出典なしの数値・断定しすぎ・誤解を招く表現）と、Experience が「なし」（体験の捏造）のとき**。Expertise・Authoritativeness が「弱い」「なし」のときは、ゲートにはせず、5-3 の該当項目の減点と、直し方の提案で扱う（上流に戻す前に、まず書き直しで足りるか考える）。
- **毎日1本、90点の記事を出せる現実的な水準にする（人の方針）**。90点を出すために、①テーマは「今の環境で出典を取れ、確認済みの体験や e-Stat などが主役になるもの」から柔軟に選ぶ ②E-E-A-T の観点が弱いテーマは、無理に書き直し続けず別のテーマに替える ③参考資料は公的機関・観光系大手企業の集計データを含む3件以上が満点。取れないときは減点（最大 -2）を許容するが、**取れないことを理由に一般論で埋めない**（5-3c）。具体の一次情報が足りないテーマは、別のテーマに替える。品質を落として90点に届かせるのではなく、届くテーマと書き方を選ぶ。
- **読み手にとっての価値**を最優先に見る。基準を満たすための水増し（文字数・見出し・キーワード）は減点・差し戻しの対象。情報の濃さは保ち、図解・表・折りたたみで文字量はスッキリ見せる（2-1）。

### 5-3c. 具体性の基準（人の方針 2026-10-12・一般論の禁止）
読み手が検索するのは、調べなければ分からない具体的な情報のため。**誰でも感覚で分かる一般論を並べた記事は、体裁が整っていても価値がない**として扱う。

- **書かないこと**: 「解体は戻せません」「補助は窓口で確認してください」「専門家に相談を」のような、読み手がすでに知っている注意や一般論を、見出し・「この記事のポイント」・表の中身にすること。「確認先の一覧表」を、具体的な情報の代わりに置くこと。注意の1文は、具体的な情報の**あとに**添えるだけにする。
- **一次情報の優先順位（E-E-A-T の Experience を最優先。人の方針 2026-10-12）**: ①RIVIA の実体験（`experience.md` の確認済みの節）と、人が `docs/sources/inbox/` に置いた一次情報 ②公に発信している運営者・当事者の事例・発言・想い（YouTube の動画と概要欄、ブログ、SNS、取材記事など。発信者名・URL・公開日つきで要約する。**RIVIA の人の実体験がなくても、これを主役にして書いてよい（人の方針 2026-10-12）**。視聴者のコメント欄は引用しない・個人名は載せない＝CLAUDE.md の絶対のルール2・9） ③統計（e-Stat など） ④国交省・国税庁・自治体などの制度ページ。**記事の主役は①②（実際にやった人にしか書けないこと）にする。④は、制度名・条件・金額を示して①②を補うために使い、④だけで組み立てた記事は「他サイトの言い換え」として扱う**。①②が足りないテーマは、④で埋めずに別のテーマに替える。人が置いた一次情報が必要なテーマは、PR の「人の確認が必要な点」ではなく、ログの引き継ぎに「◯◯の実体験メモがあれば記事化できる」と書いて、別テーマで進める。
- **各節に、具体の一次情報を最低1つ入れる**: 制度名・自治体名・金額・条件・年度・件数・実際の事例のどれか（上の優先順位の①〜④）。例: 「◯◯市の解体補助は上限◯万円・対象は◯◯（2026年10月時点）」「売却時にかかった費用の事例は、内訳が◯◯で合計◯万円（出典: ◯◯）」。
- **執筆時点を※で明記する**: 制度・金額は変わるため、「※2026年10月時点。最新は◯◯で確認」と書く。変わりうることを理由に、具体を書かないことはしない。
- **数字は、読み手の疑問と因果・関係を説明できるものだけ載せる**。説明できない数字（例: 全国の空き家数 → 迷うのは珍しくない、のような飛躍）は載せない。
- **「この記事のポイント」は、読めば得られる具体的な結論・数字・事例にする**。「〜は条件で変わります」「〜を比べます」のような中身のないポイントは書かない。
- **採点とゲート**: 「調べなくても分かる」節は、1節ごとに「独自性・一次情報」を -2。**具体の一次情報が記事全体で2件未満なら、ゲート違反（合格不可）**。戻る工程はリサーチ（具体を集め直す）。集められないテーマは、一般論で埋めずに別のテーマに替える。

### 5-3d. 理想と現実のギャップを埋める（人の方針 2026-10-12・マニュアルの存在意義）
目的は、**読み手に価値のある情報を届けること**。SEO の順位は、その結果として付いてくる。採点基準・ゲート・点数は、そのための道具であって目的ではない。理想の素材（RIVIA の実体験、人が置いた一次情報）が揃わないとき、編集長は**記事を諦めるのではなく、素材を補って、読み手に価値のある記事にする**。

- **補う順番**: ①RIVIA の実体験（確認済み）→ ②公に発信している他社・当事者の実体験（YouTube・note・ブログ・取材記事。発信者名か公開アカウントの表示・URL・公開日つきで要約。個人の自己申告であることを明記し、相場や一般論にしない）→ ③公式ページの本文を照合した具体（自治体・省庁・e-Stat）→ ④統計。①がなければ②で主役を作り、③④で補強する。**①がないことを理由に書けない、としない**。
- **取れないものは、正直に「確認できなかった」と書き、書ける範囲で価値を出す**。ただし数字・制度・体験は作らない（ゲートは緩めない）。素材が足りないテーマは、別のテーマに替えるより先に、補える素材（他社の実体験・公式ページの照合・ネットワーク許可の追加）がないかを探す。
- **品質管理部は、採点表だけでなく「読み手にとって価値があるか」を見る**。事実・出典・体験の扱いが正しく、読み手に具体が届いているなら、細かい表現の強さや条件の省略は減点にとどめ、人の確認に回して合格させる。採点のための手直しを延々と繰り返さず、**大きな価値を損なう誤りだけをゲートにする**。
- **編集長の役目**: 理想（素材・採点の基準）と実現できる範囲（環境・時間・データ）のギャップを調整する。ギャップが出たら、基準を無理に満たすことも、基準を理由に出さないことも、どちらも選ばず、**補完の手段を決めて**進める。調整の内容は PR の「人の確認が必要な点」に書く。

### 5-3e. 読み手向けの文章に、調査の裏側を書かない（人の方針 2026-10-12）
記事は、人が書いた編集記事として読めること。**AI が調べた過程の説明を、読み手向けの本文に書かない**。

- **書かない例**: 「公式サイトに接続できず本文を読めていません」「PDFの要綱は読めておらず、HTMLページの記述だけを根拠にしています」「調べたのは〜時点の本文です」「ページから確認できませんでした」「取得」「照合」「本文未照合」のような、調査手順・環境・確認方法の説明。
- **代わりに**: 事実だけを短く書く（「公式ページに載っていません」「東伊豆町と小山町は未調査です」「申請の前に、窓口で最新の要綱を確かめてください」）。時点は「2026年10月時点」と一言で足りる。出典は参考資料に載せる。
- **調査の裏側（接続できなかった、PDFが未読、検索結果の要約しか見ていない、など）は、PR の「人の確認が必要な点」と `docs/seo/log.md` に書く**。読み手に伝える必要があるのは、「この数字・条件は、いつ時点の何にもとづくか」と「最終確認は窓口へ」だけ。
- **出典の媒体名（note・YouTube・ブログなど）や「投稿者が書いています」は、本文・カード・表の中では前面に出さない**（人の方針 2026-10-12。読み手は媒体名を気にせず、媒体を知らない読み手には意味が伝わらない）。本文では事実だけを書く（「実例では200万〜400万円台」「買主が解体すると、土地価格は安くなることが多い」）。出典（媒体名・タイトル・URL・公開日）は参考資料に載せる。「個人の申告で、相場ではない」のような断りは、読み手の判断に必要なときだけ、※注記に短く置く。
- 「私たちの推測」のような、読み手の判断に必要な断り書きは残してよい（短く）。
- **データの前提条件・補足は、本文の主役にせず、「※」の注記（`<p class="table-note">※ …</p>`）にして、表や数字の近くに小さく置く**（人の方針 2026-10-12）。例: 「※ 2026年10月時点の各市町の公式ページの記載にもとづきます。金額や条件は年度ごとに変わります。東伊豆町と小山町は未調査です。」本文には結論と具体を書き、前提は注記に回す。注記も、調査の裏側の説明（接続できず・本文を読めていない）は書かない。

### 5-3f. AI が書いたような文章を書かない（人の方針 2026-10-12）
読み手が「AI が書いた」と感じた時点で、記事の価値は下がる。**人の編集者が、読み手のために書いた文章**にする。

- **書かない言い回し**: 「いかがでしたか」「参考になれば幸いです」「ぜひ参考にしてください」「〜と言えるでしょう」「〜ではないでしょうか」「〜も見逃せません」「重要なポイントです」「〜することが大切です／重要です」「結論から言うと」「まとめると」「〜について解説します」の連発、「さまざまな」「多くの」「近年では」のような中身のない水増し、全項目が同じ語尾・同じ長さの箇条書き、「まず・次に・最後に」の機械的な並べ方、感嘆符・絵文字、抽象的で当たり障りのない締め。
- **調査の裏側（接続できなかった・本文を読めていない・取得・照合・確認できませんでした）は、本文に書かない**（5-3e）。
- **書き方**: 結論と具体（数字・名前・条件・事例）を先に出す。1文は短く、主語と述語をはっきりさせる。断定できないときは、理由を短く添えて言い切る（「〜かもしれません」の連発にしない）。読み手に語りかけるより、事実を並べて判断材料にする。言い回しは、`docs/brand/voice.md` の文体に合わせる。
- 機械採点（`tools/article_score.py`）は、上の代表的な言い回しを軽い NG として減点する（1件ごと）。品質管理部は、機械が拾えない「AI くささ」（定型の構成、中身のない一般論、不自然な丁寧さ）も、ブランド準拠・読みやすさで減点する。

### 5-3g. 記事は「ひとつの主張」を通すストーリーで組む（人の方針 2026-10-12）
節を並べただけの記事（各節が短い一般論で、結局何が言いたいのか分からない）は不合格。**書き始める前に、次の4つを1行ずつ決める**（構成案に書く）。

1. **この記事で言いたいこと（主張）**: 読み終えた人が持ち帰る1文。タイトルと導入で示す。
2. **そのテーマで読み手が悩むこと**: 何につまずき、何を不安に思うか。具体的な場面で書く（調査・読者の声・RIVIA の経験から）。
3. **その悩みに対して、何をどうするか**: 判断の基準、手順、やらないこと。理由と条件つきで。
4. **実績（根拠）**: RIVIA の体験、公に発信している運営者の事例、公式の数字。数字の前提（時期・範囲）を※で添える。

節は「悩み → 解決の考え方 → 具体の進め方 → 実績 → 注意点・次の一歩」の順で、**前の節の結論が次の節の問いにつながる**ようにする。各節の頭で、その節の結論を1文で言い切り、続きに理由と具体を書く（1節は短い一般論で終わらせず、読み手が判断できるところまで書く）。節の見出しは、読み手の問い（疑問）か結論の形にする。数字だけの表を置くときは、前後で「何を示す数字か」「どう読むか」を書く。品質管理部は、この4点が通っているか（読み終えて主張が言えるか）を採点し、通っていなければ構成案まで戻す。

### 5-3h. 節は、それぞれに中身がある単位にする（人の方針 2026-10-12）
数行で終わる節（本文250字未満が目安）を並べない。**言うことが短いなら、節に分けず前後の節にまとめる。** 節にするのは、「悩みの具体」「判断の基準と理由」「実績の数字と読み方」「注意点と条件」のように、読み手が判断できるところまで書ける話だけ。記事は4〜6節を基本にし、各節に ①結論の1文 ②理由 ③具体（数字・事例・条件） を入れる。見出しだけ立てて一般論を2〜3文書くのは、読み手に何も渡さないので不合格。機械採点は、薄い節が4割を超えると減点する。既存記事の底上げでは、薄い節をまとめ直すところから始める。

### 5-3i. スマホで文字が窮屈にならない表示にする（人の方針 2026-10-12。何度も指摘された点）
スマホ（幅390px）では、文字が詰まって見えた時点で読みにくい。**内容が良くても、見た目が窮屈なら不合格**（品質管理部は読みやすさで減点し、直させる）。
- **段落・リスト・見出しの間に、十分な間隔を空ける。** 箇条書き（`ul`）・番号つき（`ol`）は、項目と項目の間に余白がある（共通 CSS で自動。`ol` は番号が見える）。文の塊を3行以上続けて置かない。
- **結論の1文（太字）のあとに、続く文やリストが「くっついて」見えないこと。** 太字の導入文のあとは、段落を分ける。
- **項目が5つ以上並ぶ、または1項目が2行を超えるリストは、カード・表・折りたたみ・図（`figure`）に変える。文字が多く縦に長くなる比較（3列以上）は、スマホで横にスワイプするカルーセルにする（比較の図 `fig--compare` は共通 CSS で自動。文章中の並びは `carousel`）。** 長い一覧は `<details class="fold">` で折りたたむ。
- **読み手が先に読まないもの（参考資料・補足・長い一覧・出典の細部）は折りたたみにする。** 参考資料は共通部品で自動で折りたたまれる（「参考資料（N件）」。中身は HTML に残るので、AI・検索エンジンには読める）。出典を長く見せたままにして、他の記事を読みたい人のスクロールを増やさない。記事の本文より下（ガイド・著者・監修者・相談）も、同じ考え方で、必要以上に縦に伸ばさない。
- **UI は、顧客視点で見直し続ける。** 新しい部品や節を足すときは、「読み手がいちばん読みたいところまでの距離が伸びないか」「スクロールが増えるだけの要素ではないか」を、スマホのスクリーンショットで確かめる。記事1本が20画面を超えるときは、折りたたみ・カルーセル・図で縮める。
- 共通 CSS（`css/style.css`）を変えるときは、全ページに効くので、サイト全体の点検（`site_check`）とスマホのスクリーンショットで確認する。
- **新規・変更した記事は、スマホ幅のスクリーンショットを自分の目で見て、「窮屈」がないか確かめる**（日次手順の最終チェックに含まれる）。見て窮屈なら、HTML化（エンジニア部）か共通 CSS で直し、記事の書き方だけで逃げない。

### 5-4. 合否と、戻る工程
- **合計90点以上、かつゲート違反なしで合格**。それ以外は不合格。（人の方針 2026-10-12: 95点から90点に緩和。記事を現実的に出し、集客につなげるため。**事実の正確さのゲートは緩めない**）
- **ゲートにしないもの（減点のみ。PR の「人の確認が必要な点」に載せる）**: 条件の一部の省略、「〜が出典より少し強い」程度の表現、参考資料が3件に届かないこと、古い掲載日の明記が足りない程度。**ゲートにするもの（不合格）**: 数字・制度・主語の取り違え、出典にない断定、体験の捏造、他者の発言の誤帰属。
- 不合格のときは、**いちばん大きく減点された項目の原因の工程まで戻る**（執筆の手直しで済ませない）。

| 減点・不合格の原因 | 戻る工程 | 担当 |
|---|---|---|
| 正確性・出典（ゲート含む）、一次情報が足りない | リサーチからやり直す | リサーチ部 → 企画 → 執筆 |
| 検索意図への回答、構成（見出し・FAQ・導線の設計）、キーワードの位置 | 構成案からやり直す | 企画・マーケ部 → 執筆 |
| 文体・読みやすさ・表記ゆれ・NG表現・文の長さ | 執筆からやり直す | 執筆担当 |
| 技術（seo_check のエラー、構造化データ） | HTML 化をやり直す | エンジニア部 |

- やり直したら、**最初から採点し直す**（前回の点数を引き継がない）。
- やり直しは1回の日次サイクルで最大5回（人の了承 2026-10-12。3回では届きにくいため）。5回で90点に届かなければ、その記事は **PR に入れず**、採点結果と原因を `docs/seo/log.md` に残して翌日の日次サイクルで続ける。**同じ記事が3日続けて不合格なら、テーマ自体を見直す**（キーワード表で「保留」にし、PR の「人の確認が必要な点」で人に相談する）。
- 合格した記事も、採点表（機械40点＋品質管理部60点の内訳）を PR の説明に載せる。
- **採点の校正**: 採点するのも AI なので、甘くなっていないかを人が確かめる。月1回、進行管理部が合格記事から1本を選び、PR に採点表と記事を並べて人に確認してもらう。人の評価と10点以上ずれた項目は、減点ルールを見直して `docs/seo/log.md` に記録する。

### 5-5. 既存記事の底上げ（人の方針 2026-10-12）
公開済み・予約中の既存記事のうち、品質管理部の採点が低いものは、**80点以上（人の方針 2026-10-12: トークンを使いすぎるときは85点でなく80点を合格とする。事実のゲートは緩めない）**を目標に書き直す（新規記事の合格点は90点。既存記事は現実的な目標として85点）。目的は、読み手に価値ある情報を届けること（5-3d の補う順番で素材を補う）。

- **対象の選び方**: `python3 tools/article_score.py` の機械採点が低いもの、一般論が多く具体の一次情報（制度名・金額・条件・年度・事例）が少ないもの、古くなった情報を含むものから順に。進行管理部が `docs/seo/calendar.md` に「底上げの待ち行列」として並べ、**上から順に、一度に直せるだけ直す**（人の方針 2026-10-12: 1日1〜2本の上限は設けない）。検索への悪影響は、記事の更新の本数ではなく中身の質で決まる（今はまだ検索への登録が進んでおらず、失う評価も小さい）。ただし、人が PR を確認できる量にするため、**1つの PR に入れるのは5〜8本ほど**を目安に、PR を分ける（衝突は `tools/sync_base.sh` が直す）。重い作業は別セッション（`Agent` の `isolation: "remote"`）に任せてよい。Vercel のデプロイ回数の上限（1日100回）があるので、push は PR ごとに1〜2回にまとめる。
- **手順**: 新規記事と同じ（リサーチ → 構成 → 執筆 → 品質管理 → HTML 化）。事実・数値・出典・体験・主張を変える書き直しは、CLAUDE.md ルール1のとおり人の確認を待つ（日次の PR に入れ、人がマージ）。
- **日付**: **公開日（`date`）は変えない**。更新日（記事データの `updated`）を、書き直しを PR に入れた日（日本時間の今日）にする。人のマージが翌日以降にずれ込む見込みなら、翌日の日付にする。更新日は `dateModified`（構造化データ）と記事の「更新日」表示に反映される。URL は変えない。
- **対象は点数が悪いものだけ**（全記事を書き直さない）。80点を超えている記事には手を入れない。
- **内容が大きく変わる場合は、書き直さず「消して新しい記事として出す」でよい**（人の方針 2026-10-12）。そのときは、旧記事の URL から新記事の URL へ **301 リダイレクト**を `vercel.json` に追加し（検索の評価と、外部からのリンクを引き継ぐ）、旧記事のデータを記事データから外す。新記事の公開日は「マージした日の翌日」（新規記事と同じ）。内部リンク・ガイド・学ぶコースの参照も新記事に付け替え、`seo_check`・`site_check`（リンク切れ）を通す。この場合は新規記事として扱い、採点は90点。
- **採点**: 80点未満なら、ゲートを満たしたうえで、いちばん減点が大きい工程に戻る（やり直しは1本あたり最大3回）。届かなければ、その記事は書き直しを見送り、ログに残す。

## 6. 人の確認が必要なもの（PR に必ず書き出す）

## 8. 誤りが見つかったとき（訂正の手順）

1. 人・品質管理部・読者の指摘などで誤りが分かったら、その日の日次サイクルで最優先で直す。
2. 記事の該当箇所を直し、dateModified と表示の更新日を新しくする。記事の末尾の注記に「YYYY年M月D日: ◯◯の記述を訂正しました」と1行残す（なかったことにしない）。
3. 同じ誤りが他の記事にないかを `grep` で全記事確認する。
4. 原因（出典の読み違い・古い資料など）を `docs/seo/log.md` に記録し、同じ誤りを防ぐルールがあれば `docs/brand/ng.md` かこの手順書に追記する。
5. 法律・税金・消防など読者に損害が出る誤りは、日次サイクルを待たずに **単独の PR（タイトル冒頭「【訂正・至急】」）** を作り、人に知らせる。直すまでの間、該当の段落を削るか「確認中」と表示する案を同じ PR に入れる。

## 9. 既存記事の見直し（鮮度管理）

- 法律・税金・補助金・統計を扱う記事は、公開から6か月ごと（または制度改正の報道があったとき）に見直す。
- 見直しのときも 5章の採点を行い、90点未満なら改善する。
- 検索での表示が3か月以上ほぼない記事は、統合・書き直し・現状維持を企画・マーケ部が判断する（削除と URL の変更は人の確認が必要）。
- **統合するとき**: 記事ファイルは削除しない。旧URLは残すか、`vercel.json` の redirects で統合先へ 301 を設定する（vercel.json の変更は人の確認）。記事データ（`tools/articles_*.py`）から外して `tools/build.py` で作り直し、全記事の本文リンクを統合先に張り替える。

## 10. 計画（plan.md）に届くための不足項目（2026-10-12 追加。編集長の自己点検）

マニュアルで決められるのは**記事の質と手順**まで。計画の数字（1記事あたり月40クリック、CTR 2.5%、CV率 0.6%）は**仮定**で、検索順位・AI検索への採用は私たちの手の外にある。「計画どおりになる」と約束はできないので、次の3つで、**外れたときに早く気づいて打ち手を変える**。


**どうしても80点に届かない記事は、削除してよい**（人の方針 2026-10-12。**今回（2026-10-12）の底上げに限った許可で、恒久のルールではない**。次回以降に削除したくなったときは、PR の「人の確認が必要な点」で人に確認する）。**定期実行（`/seo-daily`）は、基本的に記事を削除しない。** 85点に届かないときは、削除ではなく**テーマ（切り口）を変えて書き直す**（読み手の疑問・一次情報が足せる角度に。タイトルや URL を変えるときは、人の確認と 301 が要る）。原因の工程まで戻って2回直しても85点に届かない（一次情報も公式ページの具体も足せない）記事は、水増しで残さず削除する。削除するときは、①いちばん近い記事への 301 リダイレクトを付ける（`vercel.json`）②内部リンク・sitemap・llms.txt から外す（`tools/build.py` で作り直す）③PR の「変えたこと」に、削除した記事・転送先・理由を書く。他の記事に吸収できる中身があれば先に移す。

**タイトルの「収益物件になり得る理由」のような一般論の主張は、自社の実績（開業前で収支が出せない物件）がなくても書いてよい。** ただし、数字の裏づけは一次情報（公式統計・確認した公開データ・運営者の公開発信）の範囲に限り、「儲かる」とは書かない。AirDNA などの有料データは、記事の中身として確認できた数字だけを出典つきで使う（取得できなければ使わない）。

### 10-1. 先行指標の関門（届かなければ記事を増やす前に直す）
- **インデックス**: 公開から14日たっても Search Console で「登録済み」にならない記事は、記事ではなく**インデックスの問題**として最優先で調べる（robots・noindex・内部リンク・サイトマップ・リクエスト。`/seo-audit`）。2026-10-12 時点で表示回数は 0。まずここが計画のボトルネック。
- **表示回数**: 計画月ごとの表示回数が計画の70%未満なら、新記事より先に、既存記事の title・見出し・内部リンクを、実際に出ている検索語（Search Console のクエリ）に合わせて直す。
- **クリック率**: 表示があるのに CTR が計画未満の記事は、title と description を書き換える（PDCA）。
- **CV 導線**: セッションがあるのに CV が出ないときは、記事末の相談・資料請求の導線（`cta_click` の数）から直す。

### 10-2. 記事を出す前の「使ってよい事実リスト」（再発防止）
2026-10-12 の底上げで、執筆担当が `experience.md` にない設備・出来事・評価を「下田の宿の実績」として書く誤りが繰り返された（品質管理部が毎回拾えたが、差し戻しが増える）。
- 執筆を始める前に、編集長（または進行管理部）が、その記事に使ってよい**一次情報のリスト**（experience.md の確認済み節の該当行、調査メモのファイル名、既存の運営事例記事の数字）を作り、執筆担当に渡す。**リストにない体験・数字は書かせない**（書きたければ「人の確認が必要な点」に出して止める）。
- 「私たちは〜と考えます」の見解文は、事実（数字・出来事）の言い換えに使い、**根拠のない主張の穴埋めに使わない**。

### 10-3. 1日の作業量を、品質を保てる範囲にする
- 1回の定期実行で、新規記事＋底上げを欲張らない。**採点で差し戻しが多い日は、記事を増やさず、直すことに時間を使う**。使用量の上限（週次）に当たると採点自体が止まるので、PR にまとめて出せる分だけで切り上げる。
- 計画の「毎月4本」は、新規の本数。底上げは別枠で、**新規が計画を下回る週は、その理由（底上げに使った）を週次レポートに書く**。

### 10-4. 外部の動きは、人の作業に回す
被リンク、SNS・note からの導線、Search Console のリクエスト、Google ビジネスプロフィールなどは、AI 社員だけでは進められない。週次レポートに「人にお願いしたい作業」として、**1週に1〜3個、具体的に（URL つきで）**書く。

## 11. プロの SEO の考え方から取り入れること（2026-10-12 追加。人から共有された整理にもとづく）

すでにあるもの（一次情報・E-E-A-T、共食いの回避、1記事1意図、CV 計画の逆算、定期的な見直し）は省き、足りなかった点だけを、このサイトの運用に落とす。

### 11-1. 検索意図の4分類で、記事の役割と導線を決める
企画（`marketer`）は、キーワードごとに **Know（知りたい）／Do（比較・やり方）／Buy（契約したい）／Go（会社名で探す）** を決め、構成案に書く。
- **Know**: 潜在層の集客と信頼づくり（例: 空き家の固定資産税、相続登記の義務）。記事末は関連記事への導線が中心。
- **Do**: 比較・解決手段の提示（例: 売る・貸す・宿にするの比べ方、民泊と旅館業）。記事末に相談の導線。
- **Buy（購買直前）**: 流入が少なくても成約率が高い。**「費用」「比較」「事例」「運営会社の選び方」「料金」など**を最優先で作り、強化する。資料請求・相談への導線を最も強く置く。
- 記事の役割に合わせて、CV の導線を変える（Know は資料請求より関連記事、Buy は相談・資料請求）。計画（plan.md）の CV は、Buy・Do の記事から出る。

### 11-2. トピッククラスター（親と子の内部リンク）
テーマ（`sell`・`lend`・`house`・`start`・`money`・`operate`・`trend`）ごとに、**ピラー記事（全体を解説）と、深掘りの子記事**の関係を意識する。子 → 親、親 → 子の内部リンクを張る（ガイド・カテゴリページがピラーの役割）。新記事を作るときは、どのピラーの子かを構成案に書き、親にも1本リンクを足す。

### 11-3. 施策の優先順位（Quick Win を先に）
作業を決めるとき（`pm`・編集長）は、**工数が小さく、影響が大きいものを先に**する。
- **Quick Win**: 順位が11〜20位の記事の簡易リライト（検索クエリに合わせた title・見出し・追記）、CV 導線の見直し、title・description の改善。
- **後回し**: 工数が大きく、効果が不透明なもの（効果の薄いページの全面刷新）。
- 公開から **3〜6か月たった記事**は、順位・表示・CTR を確かめ、停滞している記事を優先してリライトする（不足している検索意図の追加、情報の最新化、見やすさの改善）。

### 11-4. 順位や流入が落ちたときの切り分け
感情的に直さず、次の順で分解して日次ログに書く。①範囲（サイト全体／特定テーマ／特定の記事）②要因（テクニカル: インデックス・表示・障害／アルゴリズム: 評価基準の変化／競合: より良い記事の登場）③仮説を立て、**一部で試してから全体に広げる**（PDCA 台帳に登録）。

### 11-5. AI 検索時代（GEO）の前提
- **Know だけの記事は、検索画面上で完結（ゼロクリック）して PV が減りやすい**。PV で成果を見ず、Do・Buy への導線と、**一次情報（運営の数字、失敗談、独自の見解）**で、AI の要約と差をつける。
- 生き残るのは「AI に作れない情報」: 自社の一次データ、泥臭い失敗や定性の体験、運営者の見解（playbook 5-3c・5-3d の方針の根拠）。
- 検索だけに頼らず、**YouTube・SNS・note・他サイトからの言及**で、AI（ChatGPT・Claude・Perplexity など）が参照するブランドとして認識される動きを、週次レポートで人にお願いする（playbook 10-4）。

### 11-6. 数字は事業から逆算する（PV ではなく CV・売上）
PV やセッションを成果にしない。**ターゲット外のアクセスは CV につながらない**。目標（CV）→ 必要な SEO/AIO セッション → 想定 CV 率の逆算（`tools/plan.py`）で、毎日の最優先を決める（CLAUDE.md の計画）。文字数は、情報の濃さで決める（水増しをしない。基本姿勢）。

## 12. AIO（AI に引用される）の補強（2026-10-12 追加。人から共有された整理にもとづく。参考として取り入れる）

すでにあるもの（llms.txt、robots.txt の AI クローラー許可、FAQPage の構造化データ、見出し階層・表・リスト、著者・監修者の表示、`dateModified`、一次情報と出典）は、そのまま続ける。足りなかった点だけ:

### 12-1. 引用の最小単位を意識する（チャンクで意味が通る）
AI は記事を**断片（チャンク）**で取り出す。各節は、**単独で読んでも意味が通る**ように、節の頭で結論を1文で言い切り、続けて理由・具体（数字・事例）・出典を、同じ節の中に置く（PREP: 要点→理由→具体例→要点。5-3g・5-3h と同じ形）。「前の節で述べたとおり」「上の表のように」で意味が切れる節にしない。質問への答えは FAQ に、手順は番号リスト（`<ol class="steps">`）にする。

### 12-2. E × T × R の見方（品質管理部の確認項目に足す）
- **Evidence（根拠）**: 結論に、数字・一次情報（運営の数字、公式の統計）が付いているか。
- **Traceability（追跡性）**: 出所（機関名・資料名・公表時点・URL）が、同じ節か注記で追えるか。計算した数字は、計算の元を書く。
- **Retention（定着性）**: 時点を書き、情報が古くなったとき直せるか（「2026年10月時点」の※と `updated`）。
品質管理部は、E-E-A-T の判定と並べて、この3点も見る。

### 12-3. AI 回答への引用状況を記録する
`docs/seo/ai-citations.md`（台帳）に、主要キーワード（Buy・Do を優先。playbook 11-1）を、Google の AI による概要、Perplexity、ChatGPT 等で**月1回**確かめて、記録する（引用あり／部分引用／なし、引用された URL・節、競合の引用元）。引用されない節は、PREP の形へ書き直す、FAQ にする、構造化データを足す、の順で直し、PDCA 台帳（`tools/pdca.py`）に登録する。人が確認する作業なので、週次レポートで「人にお願いしたい作業」に入れる（playbook 10-4）。AI が誤った内容で引用していたときは、その記事の該当箇所を、誤解されない書き方に直し、訂正の手順（8章）に従う。

### 12-5. 指名検索を受け止める（ゼロクリックから成果へ）
AI の回答で「アキヤド」「RIVIA&CO.」の名前が出ると、読み手は「アキヤド 評判」「RIVIA&CO. 空き家」のように**社名・サービス名で検索し直す**。
- 社名・サービス名・サービス内容を、記事の本文・FAQ・`llms.txt` で**同じ書き方で一貫して**示す（表記ゆれを作らない。`glossary`）。
- 指名検索の着地ページ（トップ・`/media.html`・`company.html`・`service-*.html`）が、「何をしている会社か」「実績（下田など）」「相談の方法」を、ファーストビューで答えているかを、月次の点検（`/seo-audit`）に入れる。実績の書き方は、非公表の方針（experience.md）に従う。
- Search Console で、**社名・サービス名を含むクエリ**の表示・クリックを月1回見て、`docs/seo/plan-tracking.md` に残す（AI 経由の認知の先行指標）。

### 12-6. AI 経由の訪問者を逃さない
AI 経由で来る人は、AI との会話で課題が整理されていて、確度が高い。AI 検索チャネル（GA4）から入った訪問の着地ページでは、①冒頭に結論（AI の回答を補う答え）②相談・資料請求の導線が、入力項目の少ないフォームに続く、を確かめる。問題があれば Quick Win（playbook 11-3）として直す。

### 12-7. サイト外での言及（サイテーション）
AI は、サイトの外で「誰がこの分野で語られているか」も見る。note、YouTube、SNS、他メディア、自治体・業界団体のページでの**言及・リンク**を増やすのは、人の作業（playbook 10-4・11-5）。週次レポートで、1〜3個、具体的に（どこに・何を・URL）お願いする。他者の発信を使うときは、公に発信している運営者の発言だけを、発信者名・URL つきで要約する（CLAUDE.md ルール2）。

### 12-8. 競合が引用されているときの直し方
`docs/seo/ai-citations.md` で競合ばかり引用されているキーワードは、競合のページにあって自社にない**数値データ・比較要素・事例**を書き出し、自社の記事に（一次情報を優先して）足す。古いデータは、AI に敬遠されるため、定期的に最新に更新する（`updated` と時点）。

## 13. ライティングの考え方から取り入れること（2026-10-12 追加。人から共有された整理にもとづく。参考として取り入れる）

すでにあるもの（結論ファースト、PREP、疑問・結論形の見出し、一次情報、引用の主従と出典、内部リンクの網、全員が同じ基準で動くマニュアル）は省き、足りなかった点だけ。

### 13-1. 冒頭（ファーストビュー）で「答えがここにある」と分かる
検索した人は、悩みを1秒でも早く解決したい。**前置き・前口上で結論を焦らさない。** 記事の冒頭（タイトル直下のリード・この記事のポイント）で、①この記事で分かること②結論（または全体像）を示す。品質管理部は、冒頭だけ読んで「自分の求める答えがある」と分かるかを見る。

### 13-2. 差別化（USP）は競合調査から決める
企画（`marketer`）は、主キーワードで上位の競合記事を数本読み、**「競合が言えていないこと」「言っているが分かりにくいこと」**を構成案に書く。それを、自社の一次情報（下田・焼津の運営、公式ページの本文で確認した数字）で埋める。USP は、特徴（Feature）ではなく、**読み手に約束できる価値（Benefit）**で書く。競合の文章は、写さず、論点の抜けだけを使う（CLAUDE.md ルール8・9）。

### 13-3. 潜在ニーズ（その先の理想の未来）まで書く
表面の検索意図（例: 「解体費の補助」）の先にある読み手の目的（「実家の負担を軽くしたい」「家族で揉めずに決めたい」「宿で収入を作りたい」）を、構成案の「読み手の悩み」に書き、結論や次の一歩を、その目的につなげる。

### 13-4. 見た目の読みやすさ（ひらく・とじる、改行、装飾）
- **漢字を詰めすぎない。** 「時（とき）」「様に（ように）」「出来る（できる）」「事（こと）」「為（ため）」「等（など）」のような、ひらいたほうが読みやすい語はひらく（目安: 漢字3割・ひらがな7割）。専門語・固有名詞は漢字のまま。`docs/brand/glossary.md` の表記を優先する。
- **スマホで3行以上、文字を詰めない。** 2〜3行ごとに段落を分ける（5-3i）。
- **強調（太字・マーカー）は多用しない。** 1画面（スクロール単位）に、強調は1か所を目安にする。節の頭の結論の1文だけを太字にし、文中のあちこちを太字にしない。

### 13-5. 「ひとり」に向けて書く（ペルソナ）
大衆に向けず、実在しそうな**特定の1人**（例: 実家の空き家を相続して、固定資産税の通知書を前に迷っている50代／副業で小さな宿をはじめたい会社員）を決め、構成案の冒頭に書く。その人の言葉で、悩みの場面から書き始める（`docs/brand/` の読者像と、ネタ箱・調査メモの声を使う。作り話の体験談にしない）。論理で納得させ、共感（悩みの場面、運営者の失敗と学び）で動かす。

### 13-6. CTA のマイクロコピー
ボタンとその直上の一言で、申込のハードルを下げ、**得られるものを明確に**する。例: 「送信する」ではなく「無料で相談する（提案までは無料・断ってもかまいません）」「資料を受け取る」。誇大な言い回し（「必ず」「リスクゼロ」）は使わない（playbook 7章）。エンジニア部は、CTA を変えたら、導線（`cta_click`・`generate_lead`）の数で効果を見る（PDCA 台帳）。

### 13-7. 読み手は「不動産・民泊・税・法律の完全な初心者」と考えて書く（人の方針 2026-10-12）
読み手は、不動産・民泊・税金・法律の知識がない人。**冒頭（タイトル直下のリード・この記事のポイント）の結論は、専門用語なしで、中学生にも分かる言葉で書く。**
- 専門用語（課税標準、譲渡所得、簡便法、特定空家、サブリース、定期借家、簡易宿所、RevPAR、稼働率、客室単価、二芯配線、旧耐震、用途地域、住宅用地の特例、控除、除却、登記 など）は、**初めて出るところで、日本語の説明か括弧書きを付ける**（例: 「稼働率（部屋が埋まっている割合）」「登記（持ち主を役所の帳簿に載せる手続き）」）。ポイントに専門用語を出すときは、その場で言い換える。
- 数字は、読み手の生活に引き寄せて書く（例: 「税が最大6倍」→「毎年の固定資産税が、土地だけの扱いになって高くなる」）。
- 手続き・制度の名前は、「何のための何か」を先に言う（制度名は後ろに括弧で）。
- 品質管理部は、ポイントとリードを、初心者の目で読み、説明のない専門用語があれば減点する（ブランド準拠）。機械採点は、ポイント・description に、説明のない専門用語があれば、軽い NG として減点する。

### 13-8. 「この記事のポイント」は、太字の1行を短く（人の方針 2026-10-12）
画面では、各項目の**最初の一文が太字の大きな文字**、残りが小さな補足になる。最初の一文が長いと、冒頭の画面がポイントだけで埋まり、読み手が本文まで進みにくい。
- **各項目の最初の一文は、45字以内**（目安は30字前後）。結論だけを言い切り、括弧書き・条件・例外は、2文目以降（補足）に回す。
- **括弧書きは、最初の一文には入れない。** 専門用語の説明は、補足の文に置く（または、言い換えで括弧をなくす）。
- ポイント全体で、スマホの1画面（約15行）に収まるのが目安。
- 機械採点は、最初の一文が45字を超える項目があると減点する。既存記事の底上げでも、ここから直す。

### 13-9. 「この記事のポイント」は、読み手にとっての意味（得・やること・注意）を言い切る（人の方針 2026-10-12）
ポイントが「制度の説明」や「条件の紹介」だけだと、読み手は「だから何？」「自分にどう関係するの？」と思う。**各項目の最初の一文は、事実そのものではなく、その事実が読み手に何をもたらすか（得・やること・避けたい損）**を言い切る。事実・条件・数字は、2文目（補足）に置く。
- 型: **「〇〇すると（なら）、△△できる／△△で済む／△△を避けられる」「〇〇の前に、△△をしておく」「〇〇だと、△△になりやすい」**。
- 悪い例: 「家主が不在とならず、宿泊室の床面積の合計が50㎡以下なら、例外として住宅の扱いになります。」→ 読み手に何の得か分からない。
- 良い例: 「小さな民泊なら、設置する消防設備が少なくて済みます。」（補足: 家主が不在とならず、宿泊室の床面積の合計が50㎡以下なら、住宅と同じ扱いになります。）
- 悪い例: 「延べ面積が300㎡未満なら、…特定小規模施設用自動火災報知設備が使えます。」→ 良い例: 「小さな建物なら、配線工事を減らして、費用を抑えられる場合があります。」（補足: 延べ面積300㎡未満なら、電池式の感知器を使う特定小規模施設用自動火災報知設備（小さな建物向けの火災報知設備）が使える場合があります。階数や状況で使えない建物もあります。）
- 守ること: ①**得を、事実以上に言い切らない**（「必ず安くなる」「儲かる」は書かない。「〜場合がある」「〜になりやすい」で、補足に条件）。②法令・税の記事は、**最終判断は窓口・専門家**を補足に残す。③読み手の生活の言葉で（費用、手間、期限、リスク）。④最初の一文は45字以内（13-8）。
- 品質管理部は、ポイントの各項目を読んで、「だから何？」と感じる項目があれば、読みやすさ・独自性で減点して直させる。

### 13-10. 本文は、ポイントと同じ流れ・同じ言い方にそろえる（人の方針 2026-10-12）
ポイント（13-8・13-9）で約束した「読み手にとっての意味」を、本文が裏づける形にする。ポイントと本文で、言い方・順番・用語がばらばらだと、読み手は迷う。
- **本文の各節の頭の結論の1文は、対応するポイントの最初の一文と同じ向き（読み手の得・やること・避けたい損）で言い切る。** ポイントの順番と、節の順番をそろえる（ポイントが4つなら、本文でも4つの話が、同じ順で追えるようにする）。
- **ポイントの補足（条件・数字）は、本文の該当の節にあること。** ポイントにあって本文にない事実を作らない（逆に、本文にあってポイントに出ない重要な話は、ポイントに足すか、節を削る）。
- 書き直しは「軽く」でよい。節の頭の1文と、つなぎの文、見出しの言い方をそろえる。事実・数字・出典・図表は変えない。
- 品質管理部は、ポイントを読んだあと、本文の各節の頭を順に読んで、「ポイントの約束が、本文で回収されているか」を確かめる。

## 14. 公開前の必要度チェックと、初心者優先（人の方針 2026-10-14）

- **14-1 必要度チェック（新規記事を書く前）**: 「民泊を始めたい初心者が、実際に検索する・悩むか」を、サジェスト・Search Console・ネタ箱・読み手の悩みで確かめる。確かめられない記事は書かない（`docs/seo/calendar.md` に理由を書いて見送る）。統計の解説・市場動向・地方創生のような「読んで知識になるが、行動の助けにならない」記事は、優先度を下げる。
- **14-2 優先順位**: 初心者がまず悩むシンプルなテーマ（いくらかかる・何から始める・失敗しない・費用と手間）を先に。専門家向けのテーマは後。迷ったら「検索する人の数」より「悩んでいる人の深さ」。
- **14-3 削除の基準**: 必要度が低い・他記事と重なる・採点が上がらない記事は、人の許可のもとで削除し、近い記事へ 301 を付ける。毎日の定期実行は削除しない（テーマを変えるのは可）。本文中のリンクは、記事を消すときに文ごと外す（宛先なしのリンクを残さない）。
- **14-4 場所の出し方**: 下田を例に使う回数は、1記事あたり必要な箇所に絞る。他の運営者の公開実績は、運営者名・URL つきで要約して使う。初めて出てくる地名は、先に説明してから使う（タイトル・この記事のポイントに、なじみのない市町村名を入れない。地域限定の記事だけ地名を入れる）。
- **14-5 トップ写真**: 記事トップ・アイキャッチに、実在する物件（改修中・売り物件など）の写真を使わない。風景・雰囲気の写真にする。
- **14-6 「だから何？」のない文を書かない**: データを並べただけの文（「〜という調査があります」だけ）で終えない。「なぜそうなるのか」「だから読み手はどうするか」を一言つける。理由が確かでないときは「〜と考えられます」と書く。分からないことを「分かりません」で終えず、考えられる理由を2〜3つ書く。
- **14-7 図は、目的と記事の例に結びつける**: 図の前後に「この図で何を見るか」を一言書き、記事で使っている例の数字を使う（例: 売上は同じ54万円の「3万円×18泊」と「2万円×27泊」で、残る利益を比べる）。
- **14-8 見回り・管理の必要性**: 法的な義務か、任意かを分けて書く。原典（空家法・自治体の案内）で確かめてから書く。
- **14-9 タイトルの長さ**: スマホで2行に収まる長さ。「｜」のあとに「・」で長い列挙を続けない。
- **14-10 プロの SEO の進め方（最小工数で最大の成果）**: ①狙う悩みを絞る→②記事を出す→③検索結果の4〜8週間後に判定→④伸びたものに追加投資・伸びないものは見出しとタイトルを直す→⑤月1回、AI引用（ChatGPT・Gemini などでの紹介）の有無を見る。やらないこと: FAQ構造化データを本文にない内容で付ける、llms.txt の作り込み、検索順位のための水増し。

### 14-11 同じ事例の出しすぎを防ぐ（下田の例・人の方針 2026-10-14）
- 1つの事例（下田の宿）を、記事ごとに何度も出さない。**1記事あたり、地名の「下田」は多くても2〜3回**にとどめる。2回目以降は「私たちの宿」「この宿」と書く。
- 事例を出す前に、他の運営者の公開実績・公的データ・取材記事（`minpaku-case-list`）で代替できないかを考える。同じ話の使い回しより、記事ごとに別の事例のほうが読み手の役に立つ。
- 下田が主役の記事（運営事例・閑散期・サービスの説明）は例外とする。
- 品質管理部は、記事ごとの地名の出現回数を数え、多い記事は差し戻す。

## 5-6 事例記事（オーナー取材）の採点基準（人の方針 2026-10-15・事例記事に限る）

取材をもとにした事例記事（`case-owner-*`、`minpaku-case-list`）は、一般の解説記事と書き方が違う。**ゲートは緩めない。採点の一部だけ、事例に合う形に変える。**

**合格ライン**: 85点以上。かつ下の「必須」に1つも当てはまらない。

**必須（1つでも欠けたら差し戻し）**
- 数字が取材原稿と一致している。取材時点（年月）と、オーナー申告であることを明記している。
- 断定を避けている（「つくれます」ではなく「この事例では〜でまかなえた」）。収益を保証しない注記がある。
- 数字の定義を書いている（純利益に何を含むか・含まないか、金額の中身）。
- 初心者向けに、専門用語を初出で説明している（OTA、公庫、転貸、用途地域など）。
- 法務・誇大・匿名性（個人の特定）の確認を通している。
- 取材から分からないこと（制度の細部・返済期間・補助金の受領額など）は、書かずに「人の確認が必要な点」へ出す。推測で埋めない。

**採点から外す（事例記事に限る）**
- 主キーワードの位置。
- 参考資料に公的機関が必要という要件（出典は「取材」でよい。制度を説明するときだけ公的な出典を付ける）。
- 一般論の「解説」の節。事例に結びつかない一般論は、書かない（水増しになる）。

**事例記事で、よく見る**
- 悩み→対処→実績の流れが、オーナーの言葉と数字で語られているか。
- 「うまくいかなかったこと」が、前の節の繰り返しになっていないか。
- 読み手が「自分にもできるか」を判断できる材料（初期費用・月の収支・手間）があるか。
- 見出しと中身が合っているか。

## 5-7 ミスリードのチェック（品質管理部の必須項目・人の方針 2026-10-15）
数字や言い方が、**書いた意図と違う意味に読まれる**ことを防ぐ。採点のたびに、次を1文ずつ確かめる（ゲート扱い。1つでも当てはまれば差し戻し）。
- **補足が数字の範囲を狭めていないか**: 「純利益は返済を引いたあとの額」と書くと、返済しか引いていないように読める。引いたものが他にもあるなら「返済などの費用を引いた額」と書く。何を含み、何を含まないか、分からないことは「確認していない」と書く。
- **一部を全体のように書いていないか**: 例を示す文が、「いつでもそうなる」と読めないか。
- **「満室」「大きく改善」「格安」など、数字の裏づけのない強い言葉**がないか。
- **前提の抜けた比較**: 費用と利益を並べるとき、期間・含む範囲・時点がそろっているか。
- **読み手が最初に誤解しそうな箇所**（ポイント、見出し、表の注記）を、初心者の目で読み直す。

### 5-6b 事例記事の独自の採点表（人の方針 2026-10-15・5-6を具体化する。一般記事の40点＋60点とは別に、これで100点満点）
`tools/article_score.py` の機械採点は、事例記事では**参考値**とし、合否はこの表で決める。合格は85点以上で、5-1・5-6・5-7 の必須に1つも当てはまらないこと。
| 項目 | 配点 | 見ること |
|---|---|---|
| 事実の一致 | 25 | 数字・時期・属性が取材原稿と一致。取材時点とオーナー申告であることの明記 |
| 数字の定義とミスリードのなさ | 20 | 何を含み何を含まないか。補足が範囲を狭めていないか。確認していないことを「確認していない」と書いているか（5-7） |
| 自分に置き換えられる | 15 | 読み手が「自分ならどうか」を考えられる材料（初期費用・月の収支・手間・前提）があるか |
| ストーリーと読みやすさ | 15 | 悩み→対処→実績の流れが切れていない。表は1行表示、対談は流れでつながる。スマホで窮屈でない |
| 失敗・限界への誠実さ | 10 | うまくいかなかったことが具体的。保証しない注記。前の節の繰り返しになっていない |
| 用語の説明 | 5 | 初出で専門用語を説明（初心者が止まらない） |

### 14-1b 需要の調べ方（サジェストが使えないとき・人の方針 2026-10-15）
新規記事の前の必要度チェック（14-1）は、次の順に使えるものを使い、**根拠を `docs/seo/calendar.md` に1行書く**。
1. **Search Console**（`python3 tools/analytics.py`）: 表示が出始めた検索語。表示が少ない間は参考にならないので、4〜8週間ごとに見る。
2. **サジェスト**（入力候補）: 許可ドメインに `suggestqueries.google.com` などが入っていれば、取得して候補を集める（`docs/seo/allowed-domains.md`）。使えないときは次へ。
3. **YouTube の検索**（`python3 tools/youtube_research.py "キーワード"`）: 同じ悩みの動画の本数と再生回数を、需要の目安にする。コメント本文は保存しない。
4. **相談フォームの内容・GA4 の入口ページ**: 実際の問い合わせ（generate_lead）の悩み、読まれているページ。
5. **取材・一次情報**（docs/sources/inbox/）: オーナーが「始める前に困ったこと」。
6. 上のどれでも確かめられないテーマは、書かずに「需要未確認」として見送る。

### 5-7b ネガティブな情報には、必ず目的をつける（人の方針 2026-10-15）
失敗・赤字・廃止率・リスクなど、読み手が不安になる情報を書くときは、**「だから読み手はどうすればよいか」を同じ段落で書く**。目的のないネガティブな情報（「〜という数字があります」「赤字の月もありました」だけで終わる文）は書かない。品質管理部は、ネガティブな文を1つずつ拾い、「なぜこれを書いたのか」が読み手に伝わるかを確かめる。

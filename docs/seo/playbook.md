# SEO / AIO 手順書（全部署共通の判断基準）

> **基本姿勢**: 読み手にとって価値のある情報を、高いクオリティで届ける。SEO/AIO はその結果として付いてくる。基準を満たすために文字数や見出しを水増ししない。情報の濃さは保ち、文字量は図解・表・折りたたみでスッキリ見せる（人の方針 2026-10-12）。

アキヤドの目的は「空き家オーナー・宿の開業検討者・観光事業者が検索する悩みに答え、サービスページとお問い合わせへつなげる」こと（`docs/site-spec.md` 5-2）。アクセス数そのものではなく、**相談につながる読者を増やすこと**を優先する。

目次: 1 キーワード ／ 2 記事の構成 ／ 3 AIO ／ 4 テクニカルSEO ／ 5 品質の採点（100点・90点合格） ／ 6 人の確認が必要なもの ／ 7 法務・炎上リスク ／ 8 誤りが見つかったとき ／ 9 既存記事の見直し

## 1. キーワードの選び方（企画・マーケ部）

- RIVIA のサービス（空き家再生／開業・運営支援／不動産協業／WEB集客／WEB採用）につながる悩みに限る。
- 優先順位: ①Search Console で順位5〜20位・表示が多いもの（既存記事の改善） ②既存記事と重ならない新しい悩み ③季節・制度改正などの時事。
- 1記事＝1つの検索意図。既存記事と意図が重なるなら新記事を作らず既存記事を強化する（共食い＝カニバリゼーションを避ける）。Search Console で同じキーワードに2本以上の記事が出ていたら、統合か役割分担を提案する。
- 検索意図の型（知りたい／比べたい／やり方を知りたい／依頼先を探したい）を構成案に書き、型に合った形（定義・比較表・手順・チェックリスト）にする。
- `docs/seo/keywords.md` に候補・担当記事・状態を記録する。
- **新規記事は週2本まで**（似た記事の量産と、Google のスパムポリシー「大量生成コンテンツの不正使用」を避けるため）。超える場合は人の確認が必要。

## 2. 記事の構成（企画・マーケ部の構成案・執筆担当）

`docs/site-spec.md`「記事ページの構成（SEO・AIO対策）」に従う。要点:

1. タイトル: 主キーワードを前半（20字以内）に。サフィックスを除いて **40文字以内**。
2. meta description: リード文と同じ要約。**50〜140文字**。
3. **この記事のポイント**: 結論を3〜5行で先に示す（AIに要約・引用されやすい）。
4. 見出し h2 は **4〜8個**。60%以上を「疑問文」か「結論」の形にする。各見出しの直後の1〜2文で、その問いに答えきる。
5. 1文は平均60字以下。80字を超える文は全体の5%以下。
6. 数値・制度には必ず出典（資料名・公表年）を付ける。出典のない数値は書かない。
7. よくある質問（3問以上）＋構造化データ FAQPage（本文と一致）。
8. 参考資料（3件以上・公的機関か、集計データを公表している観光系大手企業〈JTB・HIS など〉を含む）、公開日時点の情報である旨の注記、執筆者・監修者情報、関連サービスへのリンクと相談ボタン。
9. 内部リンク: 本文から関連する記事へ2本以上、関連サービスへ1本以上。読者の状況別ガイド（売りたい／活かしたい／副業）のどれに入るかを構成案で決める。

### 2-1. 読みやすさの基準（スマホ 390px で読む人向け。企画・執筆・エンジニア・品質管理の全員が守る）

読者の多くはスマホで読む。文字が詰まった記事は、正しくても読まれない。次を満たす。

1. **1段落は2〜3文以内**（目安150字以内）。長くなったら段落を分ける。
2. **見出しの直後は、結論の1文**。その1文は自動で太字になる（節の最初の段落の一文目）。補足は2文目以降に回す。
3. **「この記事のポイント」は1項目を短く**（要点の一文は40字以内）。補足があるときは「要点。補足。」の2文にすると、補足が小さく淡く表示される。長い注記は本文に回す。
4. **長い計算式は本文に並べない**。数値の比較は表にし、式は `<details class="fold"><summary>表の計算式を見る</summary><ul>…</ul></details>` で折りたたむ（式だけの箇条書き `<ul>` は自動で「式」の枠になる）。同じ式を何度も書かない。
5. 注意書きは `<div class="callout callout--note"><p class="callout__label">注意</p><p>…</p></div>`、節の結論を目立たせたいときは `callout callout--answer` を使う（1記事に2つまで）。
6. 表は列を4つ以内にし、先頭列を項目名にする。セルに長文を入れない。
7. **スマホで1画面（約700px）に、文字だけの塊が続かない**ようにする。目安は、段落・箇条書き・表・図のどれかが1画面に2種類以上入ること。
8. 目次は自動で折りたたまれる。見出しは短く、1行に収まる語を前に置く。
9. **スマホ1画面（約700字相当）に文章だけが続かない。3〜4画面に1回は、図・表・カード・数字ハイライトのどれかを入れる。比較・手順・数値の並びは、文章でなく部品で見せる**（カルーセルカード・要点ボックス・比較カード・数字ハイライト。書き方は `docs/seo/components.md`）。情報の濃さは保ち、文字量だけをスッキリ見せる。
10. 一覧（ガイド・学ぶ・記事一覧）に載る長い title は、記事データの `short`（表示名・〜22字）と `blurb`（補足・〜18字・省略可）で短く見せる。SEO 用の title は変えない。

## 3. AIO（AIによる検索回答）で引用されるための基準

- 定義文を1文で言い切る（「◯◯とは、△△のことです。」）。
- 比較は表、手順は番号付きリストにする。数値は「数値＋単位＋時点＋出典」をそろえて書く（例: 「約3,687万人（2024年、日本政府観光局）」）。
- 一次情報を入れる: RIVIA が実際に宿を運営して得た気づき・数値（`docs/brand/experience.md` にあるものだけを使う。作り話は禁止）。
- 他者の一次情報は、**チャンネル・アカウントとして公に発信している運営者の発言だけ**を、出典（発信者名・URL）を明記して要約で紹介する。事実の部分は公的資料で裏を取る。視聴者コメント・一般の人の投稿は「読者の悩みの発見」にだけ使い、記事に引用・要約しない。集め方と扱い方は `docs/sources/README.md`。
- 各 h2 の節は、**その節だけ読んでも意味が通る**ように書く（AI は段落単位で抜き出して引用するため）。「上記」「前述の」を使わず、主語と固有名詞を繰り返す。
- 著者・監修者・運営会社の情報（E-E-A-T）を明示する。会社名・サービス名の表記は `docs/brand/glossary.md` の正式表記で統一する（AI が同じ会社として認識しやすくなる）。
- `llms.txt` でサイトの構成と主要記事を AI に案内する（毎日 `tools/build.py` で作り直す）。
- 構造化データの Organization は、全ページで同じ名称・所在地・URL を使う（追加・変更はエンジニア部が行い、人の確認）。
- AI クローラ（GPTBot・Google-Extended など）に記事を読ませるかどうかは `seo/robots.txt` で人が決める。いまはすべて許可。変更は人の確認。
- 記事の更新日（dateModified）は、内容を実際に直したときだけ変える。誤字の修正だけで更新日を新しくしない。

## 4. テクニカルSEO（エンジニア部）

`python3 tools/seo_check.py` のエラーと、`node tools/check/site_check.js`（サイト全体の点検）の重大は必ず 0 にする。HTML は直接書き換えず、`tools/build.py` で作り直す。主なチェック項目:

- title／meta description の有無・長さ・重複、canonical、OGP
- h1 が1つ、画像の alt、内部リンク切れ
- 構造化データ（Article／FAQPage／BreadcrumbList／CollectionPage）の書式と日付の整合
- sitemap.xml の網羅性と lastmod、noindex のページが sitemap にないこと
- 日本語版と英語版の hreflang の対応
- 表示速度: カードの画像は `images/photos/w/` の WebP 軽量版（幅800）を使う。写真は原寸のまま格納し再圧縮しない（site-spec の方針）。新しい写真を足すときは、権利（自社撮影・ライセンス）を確認する（7章）。
- **画像**: 新しい写真は、人が `images/photos/` に入れたもの（自社撮影、または利用許諾を確認した素材）だけを使う。AI 生成画像・出所が分からない画像は使わない。記事の構造化データの image は、記事トップの写真にする。
- 既知の課題: 予約公開の記事は公開日前でも HTML と sitemap に載っている（`js/main.js` で画面上だけ隠している）。方式の見直しは `docs/seo/calendar.md` で管理。

## 5. 品質の採点基準（品質管理部）— 100点満点・90点以上で合格

### 5-1. 必須条件（ゲート）
次のどれか1つでも当てはまれば、**点数に関係なく不合格**。

| ゲート | 確認方法 |
|---|---|
| 事実の誤りが1件でもある | 品質管理部が出典と照合 |
| 出典を確認できない数値・制度の記述が1件でもある | 同上 |
| 重大な NG 表現（誇大・保証・断定）がある | `tools/article_score.py`（終了コード 2） |
| 7章の法務・炎上リスクに1件でも当てはまる | 品質管理部が7章のチェックリストで確認 |
| `docs/brand/experience.md` にない RIVIA の体験・実績を書いている | 品質管理部が照合 |
| `tools/seo_check.py` のエラー、または `tools/check/site_check.js` の重大が1件以上（作り直しの後） | 両ツール |
| 既存記事と主キーワード、または読者の疑問の過半が重なる（共食い・量産） | 品質管理部が `keywords.md` と既存記事の title・h2 を照合 |

**ゲートの対象と、出典の求め方（人の方針 2026-10-12）**
- ゲートの対象は **数値・制度・法律・税・固有名詞などの「事実」の主張**だけ。**見解・感想・一般論・考え方・体験の解釈は、事実と区別して書けば出典は不要**（「〜と考えます」「〜という見方があります」「一般には〜」「私たちは〜と感じました」など、事実でないと読み手に分かる書き方にする）。公的機関の情報になくてもよい。
- 出典の求め方は **発行元・資料名・年（あれば URL）を書くところまで**。出典の**証跡の保証**（本文を開いての照合、スクリーンショットや保存、複数の出典での裏取り）までは求めない。検索で確認でき、書いた出典と食い違わなければ足りる（確認できなかった数値は書かない）。
- 事実と見解が混ざる文は分ける。迷ったら、数字や制度の部分だけに出典を付け、評価の部分は見解として書く。

### 5-2. 機械採点（40点）— `python3 tools/article_score.py <原稿 or HTML>`
| 項目 | 満点 | 満点の条件 |
|---|---|---|
| title の長さ | 2 | 40字以内 |
| 主キーワードの位置 | 3 | title の前半20字以内 |
| meta description | 3 | 50〜140字 |
| この記事のポイント | 4 | 3〜5項目 |
| 見出し h2 の数 | 2 | 4〜8個 |
| 見出しの形 | 2 | 60%以上が疑問・結論の形 |
| よくある質問 | 4 | 3問以上、構造化データと一致 |
| 参考資料 | 5 | 3件以上、公的機関か観光系大手企業（JTB・HIS など）の集計データを含む |
| 他の記事へのリンク | 2 | 本文から2本以上 |
| サービスへのリンク | 2 | 1本以上 |
| 1文の平均 | 2 | 60字以下 |
| 長い文の割合 | 2 | 80字超が5%以下 |
| 軽微な NG 表現 | 4 | 0件（1件ごとに -2） |
| 表記ゆれ | 3 | 0件（1件ごとに -1） |

引用（かぎかっこ・引用ブロック）の中の表記は減点しない。**点数のために引用やレビューの原文を書き換えることは捏造としてゲート違反。**

### 5-3. 品質管理部の採点（60点）— 減点方式で、根拠を必ず書く
| 項目 | 満点 | 減点のルール |
|---|---|---|
| 正確性 | 20 | 数値・制度を1つずつ出典と照合する。表現が出典より強い（断定しすぎ）1か所 -3、時点・年度の書き漏れ1か所 -2、出典の資料名があいまい1か所 -1。（誤り・出典なしはゲートで不合格） |
| 検索意図への回答 | 10 | 構成案の「読者の疑問」のうち、答えていないもの1つ -3。見出しの直後で答えきっていない見出し1つ -1 |
| 独自性・一次情報 | 10 | RIVIA の一次情報（experience.md）または出典つきの他者の一次情報が **0件なら最大4点**。上位記事にない視点・情報が1つもなければ -3。他サイトの言い換えに見える節1つ -2 |
| ブランド準拠 | 5 | voice.md の文体ルール違反1か所 -1（呼びかけの「あなた」、感嘆符、くだけた表現など） |
| 読みやすさ・構成 | 5 | 比較なのに表がない・手順なのに番号付きリストがない 1か所 -1、段落が長すぎて読みにくい節1つ -1、スマホ1画面（約700字相当）に文章だけが3〜4画面続く箇所 1か所 -1（部品の使い方は components.md） |
| 導線 | 5 | サービスへの誘導が唐突・押し付けがましい -2、ガイド（売りたい／活かしたい／副業）への位置づけがない -1、相談ボタンにつながる流れがない -2 |
| 法務・炎上リスクの配慮 | 5 | 7章のチェックリストで、ゲートには当たらないが配慮が足りない点1つ -1（例: 「〜の場合があります」が抜けている、専門家への確認の案内がない） |

### 5-3b. 価値の基準は E-E-A-T（人の方針 2026-10-12）
「読み手にとって価値のある記事」の基準は、Google の品質評価の考え方 **E-E-A-T**（Experience 経験・Expertise 専門性・Authoritativeness 権威性・Trustworthiness 信頼性）に置く（順位を直接決める指標ではなく、価値ある記事かを測る物差し。AIO で引用されやすい条件とも重なる）。採点の100点は変えず、**品質管理部は5-3 の各項目がどの E-E-A-T にあたるかを意識して採点し、採点表の末尾に「E-E-A-T の判定」を必ず書く**（厳しくしすぎず、毎日1本出せる水準を保つ）。

| 観点 | 見ること | 主に反映される採点項目 |
|---|---|---|
| Experience（経験） | RIVIA の実体験（experience.md の確認済みの節）や、運営者の発信など、実際にやった人にしか書けない情報があるか。体験の捏造がないか | 独自性・一次情報 |
| Expertise（専門性） | 制度・数字・手順が正確で、読み手が自分で判断できる深さがあるか。上位記事にない切り口・整理があるか | 正確性、検索意図への回答、独自性 |
| Authoritativeness（権威性） | 公的機関・統計・一次資料を出典に挙げているか。著者・監修者・運営会社の情報があるか | 機械採点（参考資料）、正確性 |
| Trustworthiness（信頼性） | 事実誤り・断定しすぎ・古い情報がないか。広告・自社サービスの案内が誠実か（読み手の利益を損なわないか）。専門家への確認の案内があるか | 正確性、法務・炎上リスク、導線、ゲート |

- **差し戻しにするのは、Trustworthiness が「なし」（事実誤り・出典なしの数値・断定しすぎ・誤解を招く表現）と、Experience が「なし」（体験の捏造）のとき**。Expertise・Authoritativeness が「弱い」「なし」のときは、ゲートにはせず、5-3 の該当項目の減点と、直し方の提案で扱う（上流に戻す前に、まず書き直しで足りるか考える）。
- **毎日1本、90点の記事を出せる現実的な水準にする（人の方針）**。90点を出すために、①テーマは「今の環境で出典を取れ、確認済みの体験や e-Stat などが主役になるもの」から柔軟に選ぶ ②E-E-A-T の観点が弱いテーマは、無理に書き直し続けず別のテーマに替える ③参考資料は公的機関・観光系大手企業の集計データを含む3件以上が満点。取れないときは減点（最大 -2）を許容するが、**取れないことを理由に一般論で埋めない**（5-3c）。具体の一次情報が足りないテーマは、別のテーマに替える。品質を落として90点に届かせるのではなく、届くテーマと書き方を選ぶ。
- **読み手にとっての価値**を最優先に見る。基準を満たすための水増し（文字数・見出し・キーワード）は減点・差し戻しの対象。情報の濃さは保ち、図解・表・折りたたみで文字量はスッキリ見せる（2-1）。

### 5-3c. 具体性の基準（人の方針 2026-10-12・一般論の禁止）
読み手が検索するのは、調べなければ分からない具体的な情報のため。**誰でも感覚で分かる一般論を並べた記事は、体裁が整っていても価値がない**として扱う。

- **書かないこと**: 「解体は戻せません」「補助は窓口で確認してください」「専門家に相談を」のような、読み手がすでに知っている注意や一般論を、見出し・「この記事のポイント」・表の中身にすること。「確認先の一覧表」を、具体的な情報の代わりに置くこと。注意の1文は、具体的な情報の**あとに**添えるだけにする。
- **一次情報の優先順位（E-E-A-T の Experience を最優先。人の方針 2026-10-12）**: ①RIVIA の実体験（`experience.md` の確認済みの節）と、人が `docs/sources/inbox/` に置いた一次情報 ②公に発信している運営者・当事者の事例・発言・想い（YouTube の動画と概要欄、ブログ、SNS、取材記事など。発信者名・URL・公開日つきで要約する。**RIVIA の人の実体験がなくても、これを主役にして書いてよい（人の方針 2026-10-12）**。視聴者のコメント欄は引用しない・個人名は載せない＝CLAUDE.md の絶対のルール2・9） ③統計（e-Stat など） ④国交省・国税庁・自治体などの制度ページ。**記事の主役は①②（実際にやった人にしか書けないこと）にする。④は、制度名・条件・金額を示して①②を補うために使い、④だけで組み立てた記事は「他サイトの言い換え」として扱う**。①②が足りないテーマは、④で埋めずに別のテーマに替える。人が置いた一次情報が必要なテーマは、PR の「人の確認が必要な点」ではなく、ログの引き継ぎに「◯◯の実体験メモがあれば記事化できる」と書いて、別テーマで進める。
- **各節に、具体の一次情報を最低1つ入れる**: 制度名・自治体名・金額・条件・年度・件数・実際の事例のどれか（上の優先順位の①〜④）。例: 「◯◯市の解体補助は上限◯万円・対象は◯◯（2026年10月時点）」「売却時にかかった費用の事例は、内訳が◯◯で合計◯万円（出典: ◯◯）」。
- **執筆時点を※で明記する**: 制度・金額は変わるため、「※2026年10月時点。最新は◯◯で確認」と書く。変わりうることを理由に、具体を書かないことはしない。
- **数字は、読み手の疑問と因果・関係を説明できるものだけ載せる**。説明できない数字（例: 全国の空き家数 → 迷うのは珍しくない、のような飛躍）は載せない。
- **「この記事のポイント」は、読めば得られる具体的な結論・数字・事例にする**。「〜は条件で変わります」「〜を比べます」のような中身のないポイントは書かない。
- **採点とゲート**: 「調べなくても分かる」節は、1節ごとに「独自性・一次情報」を -2。**具体の一次情報が記事全体で2件未満なら、ゲート違反（合格不可）**。戻る工程はリサーチ（具体を集め直す）。集められないテーマは、一般論で埋めずに別のテーマに替える。

### 5-3d. 理想と現実のギャップを埋める（人の方針 2026-10-12・マニュアルの存在意義）
目的は、**読み手に価値のある情報を届けること**。SEO の順位は、その結果として付いてくる。採点基準・ゲート・点数は、そのための道具であって目的ではない。理想の素材（RIVIA の実体験、人が置いた一次情報）が揃わないとき、編集長は**記事を諦めるのではなく、素材を補って、読み手に価値のある記事にする**。

- **補う順番**: ①RIVIA の実体験（確認済み）→ ②公に発信している他社・当事者の実体験（YouTube・note・ブログ・取材記事。発信者名か公開アカウントの表示・URL・公開日つきで要約。個人の自己申告であることを明記し、相場や一般論にしない）→ ③公式ページの本文を照合した具体（自治体・省庁・e-Stat）→ ④統計。①がなければ②で主役を作り、③④で補強する。**①がないことを理由に書けない、としない**。
- **取れないものは、正直に「確認できなかった」と書き、書ける範囲で価値を出す**。ただし数字・制度・体験は作らない（ゲートは緩めない）。素材が足りないテーマは、別のテーマに替えるより先に、補える素材（他社の実体験・公式ページの照合・ネットワーク許可の追加）がないかを探す。
- **品質管理部は、採点表だけでなく「読み手にとって価値があるか」を見る**。事実・出典・体験の扱いが正しく、読み手に具体が届いているなら、細かい表現の強さや条件の省略は減点にとどめ、人の確認に回して合格させる。採点のための手直しを延々と繰り返さず、**大きな価値を損なう誤りだけをゲートにする**。
- **編集長の役目**: 理想（素材・採点の基準）と実現できる範囲（環境・時間・データ）のギャップを調整する。ギャップが出たら、基準を無理に満たすことも、基準を理由に出さないことも、どちらも選ばず、**補完の手段を決めて**進める。調整の内容は PR の「人の確認が必要な点」に書く。

### 5-3e. 読み手向けの文章に、調査の裏側を書かない（人の方針 2026-10-12）
記事は、人が書いた編集記事として読めること。**AI が調べた過程の説明を、読み手向けの本文に書かない**。

- **書かない例**: 「公式サイトに接続できず本文を読めていません」「PDFの要綱は読めておらず、HTMLページの記述だけを根拠にしています」「調べたのは〜時点の本文です」「ページから確認できませんでした」「取得」「照合」「本文未照合」のような、調査手順・環境・確認方法の説明。
- **代わりに**: 事実だけを短く書く（「公式ページに載っていません」「東伊豆町と小山町は未調査です」「申請の前に、窓口で最新の要綱を確かめてください」）。時点は「2026年10月時点」と一言で足りる。出典は参考資料に載せる。
- **調査の裏側（接続できなかった、PDFが未読、検索結果の要約しか見ていない、など）は、PR の「人の確認が必要な点」と `docs/seo/log.md` に書く**。読み手に伝える必要があるのは、「この数字・条件は、いつ時点の何にもとづくか」と「最終確認は窓口へ」だけ。
- **出典の媒体名（note・YouTube・ブログなど）や「投稿者が書いています」は、本文・カード・表の中では前面に出さない**（人の方針 2026-10-12。読み手は媒体名を気にせず、媒体を知らない読み手には意味が伝わらない）。本文では事実だけを書く（「実例では200万〜400万円台」「買主が解体すると、土地価格は安くなることが多い」）。出典（媒体名・タイトル・URL・公開日）は参考資料に載せる。「個人の申告で、相場ではない」のような断りは、読み手の判断に必要なときだけ、※注記に短く置く。
- 「私たちの推測」のような、読み手の判断に必要な断り書きは残してよい（短く）。
- **データの前提条件・補足は、本文の主役にせず、「※」の注記（`<p class="table-note">※ …</p>`）にして、表や数字の近くに小さく置く**（人の方針 2026-10-12）。例: 「※ 2026年10月時点の各市町の公式ページの記載にもとづきます。金額や条件は年度ごとに変わります。東伊豆町と小山町は未調査です。」本文には結論と具体を書き、前提は注記に回す。注記も、調査の裏側の説明（接続できず・本文を読めていない）は書かない。

### 5-3f. AI が書いたような文章を書かない（人の方針 2026-10-12）
読み手が「AI が書いた」と感じた時点で、記事の価値は下がる。**人の編集者が、読み手のために書いた文章**にする。

- **書かない言い回し**: 「いかがでしたか」「参考になれば幸いです」「ぜひ参考にしてください」「〜と言えるでしょう」「〜ではないでしょうか」「〜も見逃せません」「重要なポイントです」「〜することが大切です／重要です」「結論から言うと」「まとめると」「〜について解説します」の連発、「さまざまな」「多くの」「近年では」のような中身のない水増し、全項目が同じ語尾・同じ長さの箇条書き、「まず・次に・最後に」の機械的な並べ方、感嘆符・絵文字、抽象的で当たり障りのない締め。
- **調査の裏側（接続できなかった・本文を読めていない・取得・照合・確認できませんでした）は、本文に書かない**（5-3e）。
- **書き方**: 結論と具体（数字・名前・条件・事例）を先に出す。1文は短く、主語と述語をはっきりさせる。断定できないときは、理由を短く添えて言い切る（「〜かもしれません」の連発にしない）。読み手に語りかけるより、事実を並べて判断材料にする。言い回しは、`docs/brand/voice.md` の文体に合わせる。
- 機械採点（`tools/article_score.py`）は、上の代表的な言い回しを軽い NG として減点する（1件ごと）。品質管理部は、機械が拾えない「AI くささ」（定型の構成、中身のない一般論、不自然な丁寧さ）も、ブランド準拠・読みやすさで減点する。

### 5-3g. 記事は「ひとつの主張」を通すストーリーで組む（人の方針 2026-10-12）
節を並べただけの記事（各節が短い一般論で、結局何が言いたいのか分からない）は不合格。**書き始める前に、次の4つを1行ずつ決める**（構成案に書く）。

1. **この記事で言いたいこと（主張）**: 読み終えた人が持ち帰る1文。タイトルと導入で示す。
2. **そのテーマで読み手が悩むこと**: 何につまずき、何を不安に思うか。具体的な場面で書く（調査・読者の声・RIVIA の経験から）。
3. **その悩みに対して、何をどうするか**: 判断の基準、手順、やらないこと。理由と条件つきで。
4. **実績（根拠）**: RIVIA の体験、公に発信している運営者の事例、公式の数字。数字の前提（時期・範囲）を※で添える。

節は「悩み → 解決の考え方 → 具体の進め方 → 実績 → 注意点・次の一歩」の順で、**前の節の結論が次の節の問いにつながる**ようにする。各節の頭で、その節の結論を1文で言い切り、続きに理由と具体を書く（1節は短い一般論で終わらせず、読み手が判断できるところまで書く）。節の見出しは、読み手の問い（疑問）か結論の形にする。数字だけの表を置くときは、前後で「何を示す数字か」「どう読むか」を書く。品質管理部は、この4点が通っているか（読み終えて主張が言えるか）を採点し、通っていなければ構成案まで戻す。

### 5-4. 合否と、戻る工程
- **合計90点以上、かつゲート違反なしで合格**。それ以外は不合格。（人の方針 2026-10-12: 95点から90点に緩和。記事を現実的に出し、集客につなげるため。**事実の正確さのゲートは緩めない**）
- **ゲートにしないもの（減点のみ。PR の「人の確認が必要な点」に載せる）**: 条件の一部の省略、「〜が出典より少し強い」程度の表現、参考資料が3件に届かないこと、古い掲載日の明記が足りない程度。**ゲートにするもの（不合格）**: 数字・制度・主語の取り違え、出典にない断定、体験の捏造、他者の発言の誤帰属。
- 不合格のときは、**いちばん大きく減点された項目の原因の工程まで戻る**（執筆の手直しで済ませない）。

| 減点・不合格の原因 | 戻る工程 | 担当 |
|---|---|---|
| 正確性・出典（ゲート含む）、一次情報が足りない | リサーチからやり直す | リサーチ部 → 企画 → 執筆 |
| 検索意図への回答、構成（見出し・FAQ・導線の設計）、キーワードの位置 | 構成案からやり直す | 企画・マーケ部 → 執筆 |
| 文体・読みやすさ・表記ゆれ・NG表現・文の長さ | 執筆からやり直す | 執筆担当 |
| 技術（seo_check のエラー、構造化データ） | HTML 化をやり直す | エンジニア部 |

- やり直したら、**最初から採点し直す**（前回の点数を引き継がない）。
- やり直しは1回の日次サイクルで最大5回（人の了承 2026-10-12。3回では届きにくいため）。5回で90点に届かなければ、その記事は **PR に入れず**、採点結果と原因を `docs/seo/log.md` に残して翌日の日次サイクルで続ける。**同じ記事が3日続けて不合格なら、テーマ自体を見直す**（キーワード表で「保留」にし、PR の「人の確認が必要な点」で人に相談する）。
- 合格した記事も、採点表（機械40点＋品質管理部60点の内訳）を PR の説明に載せる。
- **採点の校正**: 採点するのも AI なので、甘くなっていないかを人が確かめる。月1回、進行管理部が合格記事から1本を選び、PR に採点表と記事を並べて人に確認してもらう。人の評価と10点以上ずれた項目は、減点ルールを見直して `docs/seo/log.md` に記録する。

### 5-5. 既存記事の底上げ（人の方針 2026-10-12）
公開済み・予約中の既存記事のうち、品質管理部の採点が低いものは、**85点以上**を目標に書き直す（新規記事の合格点は90点。既存記事は現実的な目標として85点）。目的は、読み手に価値ある情報を届けること（5-3d の補う順番で素材を補う）。

- **対象の選び方**: `python3 tools/article_score.py` の機械採点が低いもの、一般論が多く具体の一次情報（制度名・金額・条件・年度・事例）が少ないもの、古くなった情報を含むものから順に。進行管理部が `docs/seo/calendar.md` に「底上げの待ち行列」として並べ、**上から順に、一度に直せるだけ直す**（人の方針 2026-10-12: 1日1〜2本の上限は設けない）。検索への悪影響は、記事の更新の本数ではなく中身の質で決まる（今はまだ検索への登録が進んでおらず、失う評価も小さい）。ただし、人が PR を確認できる量にするため、**1つの PR に入れるのは5〜8本ほど**を目安に、PR を分ける（衝突は `tools/sync_base.sh` が直す）。重い作業は別セッション（`Agent` の `isolation: "remote"`）に任せてよい。Vercel のデプロイ回数の上限（1日100回）があるので、push は PR ごとに1〜2回にまとめる。
- **手順**: 新規記事と同じ（リサーチ → 構成 → 執筆 → 品質管理 → HTML 化）。事実・数値・出典・体験・主張を変える書き直しは、CLAUDE.md ルール1のとおり人の確認を待つ（日次の PR に入れ、人がマージ）。
- **日付**: **公開日（`date`）は変えない**。更新日（記事データの `updated`）を、書き直しを PR に入れた日（日本時間の今日）にする。人のマージが翌日以降にずれ込む見込みなら、翌日の日付にする。更新日は `dateModified`（構造化データ）と記事の「更新日」表示に反映される。URL は変えない。
- **対象は点数が悪いものだけ**（全記事を書き直さない）。85点を超えている記事には手を入れない。
- **内容が大きく変わる場合は、書き直さず「消して新しい記事として出す」でよい**（人の方針 2026-10-12）。そのときは、旧記事の URL から新記事の URL へ **301 リダイレクト**を `vercel.json` に追加し（検索の評価と、外部からのリンクを引き継ぐ）、旧記事のデータを記事データから外す。新記事の公開日は「マージした日の翌日」（新規記事と同じ）。内部リンク・ガイド・学ぶコースの参照も新記事に付け替え、`seo_check`・`site_check`（リンク切れ）を通す。この場合は新規記事として扱い、採点は90点。
- **採点**: 85点未満なら、ゲートを満たしたうえで、いちばん減点が大きい工程に戻る（やり直しは1本あたり最大3回）。届かなければ、その記事は書き直しを見送り、ログに残す。

## 6. 人の確認が必要なもの（PR に必ず書き出す）

- 法律・税金・補助金・消防など、間違えると読者に損害が出る記述（合格していても、該当箇所を一覧にする）
- RIVIA の実績・数値・事例（`docs/brand/` にないもの）
- サービス内容・料金・会社情報の変更
- デザイン（CSS）・JavaScript・`vercel.json` の変更
- 記事の削除、URL の変更、公開済み記事の title の変更
- 7章で「迷ったら人に確認」に当たるもの
- **監修者の表示**: 記事には「監修：石原 佑真」が表示されている。**監修者本人が PR のプレビューで全文を読んでマージすることを、監修の確認とみなす**（2026-10-10 に人が決定。コメントは不要）。そのため PR の説明には「監修の対象になる記事（新規・大きく直した記事）」の一覧と、特に読んでほしい箇所（法律・税金・数値）を必ず載せる。
- **AI の利用の表示**: サイトや記事に AI の利用は書かない（2026-10-10 に人が決定）。記事の中で「AI が書いた」「AI によると」などと書かない。
- **RIVIA の許認可・登録**（宅建業免許、住宅宿泊管理業の登録、提携する行政書士の有無など）には記事で触れない（2026-10-10 に人が決定）。

## 7. 法務・炎上リスクのチェックリスト（品質管理部が全記事で確認）

当てはまれば **ゲート違反（不合格）**。判断に迷うものは不合格にしたうえで、PR の「人の確認が必要な点」に書く。具体的な言い換えは `docs/brand/ng.md`。

| 観点 | ゲート違反になるもの | 主な根拠 |
|---|---|---|
| 誇大・有利誤認 | 根拠のない「必ず」「確実」「No.1」「業界初」「最安」、収益・利回り・採択の保証、実際より有利に見せる比較 | 景品表示法（優良誤認・有利誤認） |
| 広告であることの明示 | 他社の商品・サービスを、対価を受けて紹介しているのに広告と表示しない | 景品表示法（ステルスマーケティング規制、2023年10月〜） |
| 不動産の広告 | 物件の取引条件を誤認させる表示、「掘り出し物」「格安」などの根拠のない表現 | 宅地建物取引業法（誇大広告の禁止） |
| 違法な営業を勧める | 届出・許可なしの営業、営業日数の上限を超える運営、無登録の管理業者への委託を勧める・容認する | 住宅宿泊事業法・旅館業法 |
| 投資の勧誘 | 特定の投資商品の購入を勧める、元本や利回りを約束する | 金融商品取引法の趣旨・ng.md 6章 |

## 8. 誤りが見つかったとき（訂正の手順）

1. 人・品質管理部・読者の指摘などで誤りが分かったら、その日の日次サイクルで最優先で直す。
2. 記事の該当箇所を直し、dateModified と表示の更新日を新しくする。記事の末尾の注記に「YYYY年M月D日: ◯◯の記述を訂正しました」と1行残す（なかったことにしない）。
3. 同じ誤りが他の記事にないかを `grep` で全記事確認する。
4. 原因（出典の読み違い・古い資料など）を `docs/seo/log.md` に記録し、同じ誤りを防ぐルールがあれば `docs/brand/ng.md` かこの手順書に追記する。
5. 法律・税金・消防など読者に損害が出る誤りは、日次サイクルを待たずに **単独の PR（タイトル冒頭「【訂正・至急】」）** を作り、人に知らせる。直すまでの間、該当の段落を削るか「確認中」と表示する案を同じ PR に入れる。

## 9. 既存記事の見直し（鮮度管理）

- 法律・税金・補助金・統計を扱う記事は、公開から6か月ごと（または制度改正の報道があったとき）に見直す。
- 見直しのときも 5章の採点を行い、90点未満なら改善する。
- 検索での表示が3か月以上ほぼない記事は、統合・書き直し・現状維持を企画・マーケ部が判断する（削除と URL の変更は人の確認が必要）。
- **統合するとき**: 記事ファイルは削除しない。旧URLは残すか、`vercel.json` の redirects で統合先へ 301 を設定する（vercel.json の変更は人の確認）。記事データ（`tools/articles_*.py`）から外して `tools/build.py` で作り直し、全記事の本文リンクを統合先に張り替える。

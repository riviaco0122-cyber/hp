# 日次 SEO/AIO サイクル（編集長の手順）

あなたは編集長です。`CLAUDE.md` のルールに従い、各部署（`.claude/agents/`）に Agent ツールで仕事を振り、結果を PR にまとめます。**2日に1回（日本時間の月・水・金。人の方針 2026-10-24）動くので、1回の量は少なく・確実に**。終わらなかったものは次の実行に引き継ぎます。

**部署への依頼は、必ず待ってから次へ進む（人の指示 2026-10-16）。** Agent ツールは `run_in_background: false`（前景）で呼び、結果が返ってから次の工程に進む。**バックグラウンドで依頼して、自分の返答を先に終えない。** 定期実行は、最初の返答が終わった時点で「完了」とみなされ、完了メールもそのときに送られる。途中で返答を終えると、記事が仕上がる前に「完了」になり、最終の要約がメールに載らない（2026-10-16 に実際に起きた）。最後の要約（手順の 8.）を書くまで、1回の返答の中で最後までやり切る。

## 休止日（人の指示 2026-10-12）
- **日本時間の 2026-10-13（火）は休み。** この日に起動したときは、ブランチも作らず、ファイルも変えず、PR も出さず、通知も送らず、「休止日のため何もしません」と1行だけ書いて終了する。**定期実行の記事づくりは、翌日 2026-10-14（水）から再開する。**
- 休止日の判定は、日本時間の日付で行う（`TZ=Asia/Tokyo date +%F`）。2026-10-13 以外は、通常どおり以下を実行する。

## 0. 準備（ブランチの決め方）
1. 本番ブランチ（GitHub のデフォルトブランチ）を調べ、最新を取得する。以下 `$BASE` と書く。
   ```bash
   BASE=$(git ls-remote --symref origin HEAD | awk '/^ref:/{sub("refs/heads/","",$2); print $2}')
   git fetch origin "$BASE"
   ```
2. 作業ブランチは **`seo/daily` に固定**する。
   - `origin/seo/daily` があり、まだ `$BASE` にマージされていなければ（人の確認待ち）、それをチェックアウトし、`git merge origin/$BASE` で本番ブランチの変更を取り込んでから、その上に今日の作業を積む。PR は既存のものを使い、説明文を更新する。
   - なければ（前回分がマージ済み）、`origin/$BASE` から `seo/daily` を作り直す。
3. `python3 -m pip install -q -r tools/requirements.txt budoux beautifulsoup4 pillow yt-dlp`（集客データの取得と生成スクリプト用。`pip` と `python3` の版が違う環境があるので、必ず `python3 -m pip` で入れる。失敗しても続行）。集客データの取得で `cryptography`・`cffi` のエラーが出たら `python3 -m pip install -q -U cffi cryptography` で入れ直してからやり直す（Debian 版が入っていて `-U` が失敗するときは `python3 -m pip install -q --ignore-installed cffi cryptography`。2026-10-12 に動作確認済み）。`GOOGLE_SERVICE_ACCOUNT_JSON` などの環境変数がない場合は、ルーティンの実行環境が「アキヤド」（鍵を登録した環境）になっているかを人に確認してもらうよう、要約に書く。
4. **`python3` が 3.11 のときは `python3.12` を使う（build.py の f-string が 3.12 の構文で、3.11 では動かない。依存は `python3.12 -m pip install --break-system-packages -r tools/requirements.txt budoux beautifulsoup4 pillow yt-dlp`。2026-10-23 に確認）。** 以降の `python3 tools/…` もすべて `python3.12` で実行する。`python3 tools/build.py` でサイトを作り直す（公開日を迎えた記事を llms.txt・sitemap に反映するため。毎回必ず。差分が出たらその日の PR に含める）。
   - 作り直しは毎回、記事データ（`tools/articles_*.py`）と `tools/build.py` から行う。**HTML を直接書き換えない。**
5. **未マージの記事の公開日を確認する**：**新規記事の公開日は「人が確認してマージした日の翌日」にする（人の方針 2026-10-12）**。人は実行の当日にマージするので、`seo/daily` に入っている未マージの新規記事は、毎回「今日（日本時間）＋1日」に付け直す（過去の日付で公開しないため。前回の予約記事と日付が重なっても、1日2本までは可）。既にマージ済みの予約記事は変えない。
6. **人の確認が追いついているか**：未マージの PR が5日以上たっている、または未マージの新規記事が3本以上あるときは、新規記事を作らない。ログ・既存記事の訂正だけにして、PR の冒頭で人にマージを依頼する。記事の在庫は、マージ済みの記事だけで数える。
7. **大きな災害・事件のとき**：気象庁の警報や大規模な災害・事件の報道があるときは、新規企画で災害・被災地を扱わない。被災地域や関連するテーマの予約記事は、公開日を延ばす案を PR に出して人の判断を仰ぐ。

## 1. 曜日ごとの重点（日本時間）

**実行のたびに、新規記事を1本作る（人の方針 2026-10-15）。** 下の曜日の重点は「新規記事に加えてやること」。既存記事の底上げは、新規記事を出したうえで余力があるときだけ（人の指示があるときを除く）。

## 2. 毎回の流れ
0. **計画に対する進み具合（毎回・最初に）**：`python3 tools/plan.py check` で、計画月（2026-10-11 を初日に1か月ごと）の実績（検索の表示回数・クリック・AI検索・SEO/AIO セッション・CV）を CV 計画（`docs/seo/plan.md`）の日割りと比べる（結果は `docs/seo/plan-tracking.md` に追記される）。出力の「今日の最優先」（計画の木でいちばん上流の遅れ）を、その日の作業の1つ目にする。遅れの打ち手が施策台帳にまだなければ `marketer` に登録を依頼する。API が使えないときは、その旨をログに書いて続ける
1. **PDCA の Check（毎回）**：`python3 tools/pdca.py check` を実行し、測定日を迎えた施策を判定する（API を使うのは測定日を迎えた施策があるときだけ）。判定が出たら `marketer` に次の一手と学びの記録（Act）を依頼する。
2. **洗い出し**：進行管理部 `pm` の仕事A。新規記事のテーマは、playbook 1章の**テーマの柱の配分**（1週間の3本を ③宿の集客 1本・④宿の人材・採用 1本・①②（売る・貸す・開業・税金など）か時事 1本。週1本は必ず集客・採用以外）を守るように選ぶ（`marketer` が直近7日を数える）。**0. の「今日の最優先」**・曜日の重点・引き継ぎ・台帳から、今日の作業（最大3件）を決める。1件目は計画の遅れを取り戻す作業にする（遅れがなければ曜日の重点どおり）。
3. **実行**：作業ごとに担当部署へ依頼する。
   - 記事（新規・書き直し）は必ず次の順。**品質管理部の採点が90点以上・ゲート違反なしになるまで先へ進めない**（playbook 5章）。
     0. **ネタ収集（毎回。人の方針 2026-10-22）**：`.claude/skills/trend-research/SKILL.md` の3経路で集める。編集長が `python3 tools/yt_trend.py "テーマの語" --transcripts 3`（伸びている動画と上位の字幕・概要欄。Bash の timeout 600000・前景）を実行し、必要なら `python3 tools/youtube_research.py "キーワード"`（コメントの傾向）も実行して、結果を researcher に渡す。researcher は X（WebSearch を x.com に絞る）とネット検索（ディープリサーチ）を自分で行い、X の投稿 URL は編集長が `python3 tools/x_post_date.py <URL...> --days 180` で日付を出して返す。集めた「読者の声」（一般の人の投稿・コメントを名前なしで要約）は、記事の悩み・事例の肉付けに使う（公的な話だけの記事にしない）
        統計の数字（宿泊者数・外国人の割合・空き家数・空き家率など）が要る記事は、編集長が `python3 tools/estat.py lodging <都道府県>` ／ `akiya <地域>` ／ `search "キーワード"` で e-Stat から取り、結果（`docs/sources/estat/`）を researcher に渡す。**統計の数字は e-Stat から取り、出典（統計名・調査年・表の名前・e-Stat の URL）を付ける**。ほかのサイトの数字を孫引きしない
     1. `researcher`（リサーチメモ）→ `marketer`（構成案）→ `writer`（原稿。自己採点で機械40点にしてから提出）
     2. `qa` が原稿を採点。90点未満なら、`qa` が指定した **戻る工程**（リサーチ／構成案／執筆）からやり直し、最初から採点し直す
     3. 合格したら `engineer` が記事データ（`tools/articles_auto.py`）に足し、`python3 tools/eyecatch.py <スラッグ>` でアイキャッチを作って `python3 tools/build.py` で作り直す → `qa` が HTML を採点（90点以上・seo_check エラー0・site_check 重大0）。不合格なら同じく戻る
     4. やり直しは1回の実行で最大3回（人の方針 2026-10-23。ネタ収集で素材を厚くしたため）。届かなければ PR に入れず、採点結果をログに残して次の実行に続ける（3回続けて不合格ならテーマを保留にして人に相談）
   - 技術改善は `engineer` → `qa`。
4. **最終チェック**：
   - `node tools/check/site_check.js --out /tmp/site_check.md` で **サイト全体の点検**（全ページ×スマホ・PC、本番との見た目の比較）。**重大が1件でもあれば PR を出さない**（原因を直すか、その日の変更から外す）。見た目の差分が大きいページは、意図した変更かを確かめて PR に書く。
   - **スマホ幅のスクリーンショットを自分の目で確認する**（Playwright で幅 390px、予約公開の記事は `?preview=1`。画像を Read で開いて見る）。対象は、新規・変更した記事と、**共通 CSS（`css/style.css`・`js/main.js`・`tools/figures.py`・`tools/build.py` の部品）を変えた日は全記事**。図（fig-point・fig-col・fig-step・fig-cyc・fig-flow・計算式の枠）・表・番号つきリスト・注意枠・折りたたみ・目次・画像について、**左右の余白（番号や文字が枠の左端にくっついていないか）・文字のはみ出し・重なり・固定の相談ボタンの被り**を見る。`site_check` の「見た目の崩れ」などの警告も 0 にする（出たら css・figures.py・記事データを直して作り直す）。
   - `python3 tools/seo_check.py` のエラーが 0 であること。
   - 記事を新規・変更した日は `node tools/check/text_runs.js`（スマホ幅で「文章だけが続く高さ」を測る。1400px 以上の記事が0本であること。超えたら図解・表・カードで区切る）。
   - `qa` に `git diff origin/$BASE` 全体を採点してもらい、「人の確認が必要な点」を出す。
5. **記録とPR**：`pm` の仕事B（カレンダー・ログ・ダッシュボード・台帳・PR説明）。
6. **衝突を自動で直す（人の方針 2026-10-12）**：人はスマホでプレビューを見てそのままマージするだけにしたいので、PR に衝突を残さない。コミットの前後で `bash tools/sync_base.sh` を実行し、本番ブランチの取り込みと衝突の自動解消（log 等は両方残す／ダッシュボードと生成物は作り直す）を行う。終了コード 2（自動で直せない衝突）のときは、衝突ファイルを自分で読んで解消し、`python3 tools/build.py` → seo_check → site_check をやり直す。解消後に再度 `bash tools/sync_base.sh` が「衝突なし」になるまで繰り返してから push する。push 後、PR が「衝突あり」のままなら、その場で直す。
   6. `bash tools/check_secrets.sh` で鍵が混ざっていないことを確かめてから、コミット（「日次SEO YYYY-MM-DD: 〜」）→ `git push -u origin seo/daily` → `$BASE` 向けの PR がなければ作成、あれば説明文を更新。PR タイトルは「SEO/AIO 改善（YYYY-MM-DD〜）」。
   - **PR の説明の冒頭に「確認用リンク」を必ず書く（人の方針 2026-10-12）**：人はスマホでプレビューを開くだけなので、新規・更新した記事ごとに `/media/<スラッグ>.html?preview=1`（記事名つき）を一覧にする。プレビューの URL（Vercel の bot がコメントするもの）の後ろにつなげて開く。`?preview=1` を付けると、公開日前（予約公開）の記事も、そのタブの中では一覧・記事ページに表示される（`js/main.js`。付けないと予約記事は記事一覧に戻されて見えない）。
   - **PR を作ったら、完全なプレビュー URL を作って通知に載せる（人の方針 2026-10-12）**：Vercel の bot のコメント（`get_comments`）から Preview の URL（例 `https://hp-git-seo-daily-rivia3.vercel.app`）を読み、新規・更新した記事ごとに `<Preview の URL>/media/<スラッグ>.html?preview=1` を作る。PR の説明の冒頭の確認用リンクを、この完全な URL に書き換え（`update_pull_request`）、PushNotification の本文（完了メール）と最終メッセージにも同じ URL を載せる。bot のコメントがまだなければ、少し待って（Bash の sleep は使わず、他の作業を挟んで）もう一度読む。
7. **本番ブランチへのマージはしない**（人の最終確認のため）。
8. 最後に、その日の作業の要約（**計画に対する進み具合の1行（CV と最優先の指標・判定）**・やったこと・PR の URL・人に確認してほしいこと・採点結果・点検結果）を、最終メッセージとして短くまとめる（定期実行の完了メールに載る）。**月曜は週次レポートの要点（先週の数字と計画比、計画月の進み具合、今週の最優先）を冒頭に載せる。**
   - **通知を送る（人の指示 2026-10-17。毎回必ず）**：最終メッセージを書く直前に、`ToolSearch` で `select:PushNotification` を読み込み、`PushNotification` を `status: "proactive"` で1回呼ぶ。本文は200文字以内・1行・記号なしで、人が次にやることを先頭に書く（例：「アキヤド日次 10/17：新規記事『会社員の民泊副業』のPR #91 を確認・マージしてください。採点96点、点検問題なし」）。PR を出せなかった日・止まった日も、その理由を1行で送る。ルーティンのメール・プッシュの通知は、この呼び出しで「知らせるべき結果」と判断されて送られるため、省略すると人に届かない（2026-10-16・17 に実際に届かなかった）。「送られなかった」と返ってきても、そのまま続けてよい

## テーマが難しいときは別のテーマを探し、背景を通知する（人の方針 2026-10-15）
- 考えていたテーマが難しい（一次情報の本文が取れない、体験・事例の素材がない、採点が届かない など）ときは、そこで止まらず、**別のテーマを探して新規記事を1本作る**。
- **新規記事0本で終えてよいのは、需要を確かめたテーマを3つ試しても、どれも90点に届かなかった日だけ**（人の方針 2026-10-29）。テーマを1つ見送っただけで0本にしない。素材が薄いときは、取れる一次情報（条文・公的資料・e-Stat・確認済みの体験・公に発信している当事者の事例）が主役になる切り口に替える。0本の日は、試した3つのテーマと、それぞれの見送りの理由をログ・通知に書く。
- 止めたテーマは、**何が難しかったか（どのドメインが 403 か、どの素材が足りないか、採点の減点理由）**と、人にしてほしいこと（ネットワーク許可の追加、素材の提供）を、PushNotification の本文・最終メッセージ・`docs/seo/log.md` に必ず書く。別テーマでも出せなかった日も同じ。
- 人にしてほしいこと（許可の追加など）で次回以降に作れるようになるテーマは、ログの引き継ぎに残す。

## 人の確認は PR のマージ（最終確認）だけ。途中では止まらず最後まで書く（人の方針 2026-10-15）
- 定期実行では、**人にメモや許可を頼んで作業を止めない。** 素材（体験メモ・許可ドメイン）が足りなくても、取れる一次情報（条文・公的資料・確認済みの体験・公に発信している当事者の事例）で、**別の切り口・別のテーマに替えてでも、その日のうちに新規記事を1本、PR まで仕上げる。**
- 人へのお願い（メモ・ネットワーク許可）は、作業を止める理由ではなく、**次回以降を良くするための追記**として、通知・ログの引き継ぎに書くだけにする。
- 品質の基準（採点90点以上・ゲート・事実を作らない・確認済みでない体験を使わない）は下げない。基準に届くまで、原因の工程に戻って直す（上限は1回の実行で3回）。

## タイトルは「読むと何が分かるか」が一目で分かるように。本文は初心者向けに（人の方針 2026-10-15）
- **タイトルは、その記事を読めば何が得られるかが、専門語なしで一目で分かる形にする。** 「条文の数字」「窓口の順番」のような抽象語や言い換えは避け、「〇〇のやり方｜必要なもの・手順・相談先をやさしく解説」のように、読み手の知りたいこと（やり方・金額・条件・流れ）をそのまま書く。構成案の段階で、タイトル案を2〜3個出して、いちばん分かりやすいものを選ぶ。

- **検索結果での見え方を意識する（人の方針 2026-10-17）**: 検索結果ではタイトルしか読まれないことが多く、Google は長いタイトルを切ったり「｜」の片側だけを出したりする。①「｜」より前だけを読んでも**民泊・空き家・宿の話で、何が分かるか**が伝わる（「｜」は1つまで）②主題の語（民泊・空き家・宿など）を前半に③サフィックス除き40字以内（できれば32字前後）④「ほぼ満室なのに赤字の民泊」のような、ひと目で意味が取れない言い回し・体言止めのつなぎ方をしない（声に出して読み、意味がすっと入るか確かめる）。`seo_check` の「｜より前に主題の語がない」警告は0にする。詳しくは playbook 2章。
- 品質管理部の採点でも「初心者が最後まで読めるか」「タイトルで得られるものが分かるか」「検索結果で『｜』より前だけ見ても民泊・空き家の話と分かるか」を見る。

## テーマは必ず需要を確かめてから決める（人の方針 2026-10-15）
- **需要が確認できたテーマだけを採用する。** 素材（体験・条文・データ）が揃っているだけでは採用しない。順番は「①需要の確認 → ②素材が取れるか → ③既存記事との重なり」。

## テーマの選び方（人の方針 2026-10-12）
記事のテーマは固定しない。キーワード表の候補にこだわらず、**読み手が知りたい具体（制度・金額・条件・事例）を、WebSearch・e-Stat・確認済みの体験で取れて90点を満たせるテーマ**（e-Stat・確認済みの体験・実行環境で開ける資料が主役になるもの）を、毎回柔軟に選ぶ。取れないデータが要るテーマは、無理に書き直し続けず、別のテーマに替える。

## 作業が重いとき（人の方針 2026-10-12）
1回の実行に詰め込みすぎない。重い作業（全記事のデザイン直し、複数記事の書き直し、大きな調査など）は、次のように柔軟に分ける。
- その日の PR は小さく保ち、1つの PR に1つの目的だけを入れる。重い作業は、独立した PR に分ける（衝突は `tools/sync_base.sh` が直す）。
- 実行環境が許せば、重い作業は別セッション（`Agent` の `isolation: "remote"`）に任せてよい。使えない場合は、作業を小さな単位に切り、残りを `docs/seo/log.md` の「次回への引き継ぎ」に具体的に書いて、次回以降の実行で続ける。
- **Vercel のデプロイ回数に上限がある**（無料プランは1日100回。超えると「Deployment rate limited — retry in 24 hours」となり、本番にも反映されない）。push のたびにデプロイが走るので、途中経過の WIP コミットを何度も push しない。作業はまとめて1〜2回の push にし、マージも必要な分だけにする。`vercel.json` の `ignoreCommand` で、本番ブランチと `seo/daily` 以外のブランチのビルドはスキップする（人が見るプレビューは `seo/daily` だけ）。
- **新規記事1本は削らない**（人の方針 2026-10-29）。時間・使用量が足りないときに削るのは、底上げの本数・技術改善・月1回の点検など、新規記事以外の作業（次の実行に回す）。品質を落として終わらせることもしない。

## 判断は自動で決める（人の方針 2026-10-12）
表記のそろえ方（丸めの誤り・用語の統一）、出典リンクの付け方、一般的な注意の1文の追加、PR の確認用リンクの整え方のように、**どちらが適切かが資料やルールから決められること**は、人に聞かず編集長が決めて直す。事実・数値・出典・体験・主張を変える場合は、出典で裏づけられるものに限り直し、PR の「人の確認が必要な点」に「こう直した」と書く。人に聞くのは、テーマの差し替え・体験の使い方・法務/税の判断・公開日など、資料やルールから決められないものだけ。参考資料には、確かめた URL を `sources` の各行の末尾に付ける（`発行元「資料名」（年） https://…`。画面では資料名がリンクになる）。

## 理想と現実のギャップは編集長が埋める（人の方針 2026-10-12）
目的は読み手に価値ある情報を届けること（SEO はその結果）。素材（自社の実体験・一次情報）が理想どおりに揃わなくても、**他社・当事者の実体験の補完、公式ページの照合、ネットワーク許可の追加などで補い**、品質を保って記事にする。基準を理由に出さない、基準を満たすためだけに手直しを繰り返す、のどちらもしない。詳しくは playbook 5-3d。

## スマホ版のバランスの悪さは自分で直す（人の方針 2026-10-12）
スマホ幅（390px）で、表の1列目が細く文字が縦に伸びる、左右の余白がない、文字が枠からはみ出す、といったバランスの悪さは、人に言われる前に自分で直す。
- **表**: `tools/build.py` の `auto_stack_tables` が、1列目が12字を超える、または他の列に24字を超えるセルがある表を自動でカード表示（`table--stack`・各セルに `data-label`）にする。手書きで `<div class="table-scroll table-scroll--stack">` を書くときは、閉じの `</div>` を書かない（build が足す）。
- **点検**: `site_check` が、スマホ幅の「見た目の崩れ」（余白・はみ出し・重なり）と、1列目が細く縦に伸びた表を警告する。警告が出たら、`css/style.css`・`tools/figures.py`・記事データを直して作り直し、警告 0 にしてから PR を出す。
- **目視**: 新規・変更した記事は、スマホ幅のスクリーンショットを自分の目で見て、表・図・カルーセル・折りたたみの余白とバランスを確かめる。気になる箇所があれば、直してから出す。

- **具体的な一次情報が取れないテーマは書かない／取れる範囲で必ず具体を入れる（人の方針 2026-10-12・旧「取れないデータは使わない」を改める）**：読み手が欲しいのは、調べないと分からない具体（どんな補助が、いくらで、どの条件であるか。売却時に実際にいくらかかった事例、など）。一般論（「窓口で確認を」「専門家に相談を」）を並べて90点に届かせることはしない（playbook 5-3c）。**記事の主役は、RIVIA の実体験、または公に発信している運営者・当事者の事例・発言・想い（`python3 tools/youtube_research.py "キーワード"` の動画情報・概要欄、ブログ、取材記事。発信者名・URL つきで要約。RIVIA の実体験がなくても書いてよい）、（`experience.md` の確認済みの節）・人がネタ箱に置いた一次情報・公に発信している運営者の事例（E-E-A-T の Experience。playbook 5-3c の優先順位①②）。制度ページなどの公的情報は、それを補う脇役**。実体験が足りないテーマは、公的情報で埋めずに別のテーマに替える。公的情報は、**公式ページ（自治体・省庁・e-Stat など）の本文を開いて照合できたものだけ**を記事に書く。この環境では WebFetch が使えない（名前解決に失敗する）ので、**編集長が Bash で `python3 tools/fetch_text.py <URL>` を実行して本文を取得し（許可済みのドメインだけ。保存先は /tmp/akiyado-pages/）、そのファイルを researcher・writer に渡す**（researcher は Bash を持たない）。403 で取得できないドメインは、環境のネットワーク許可に足してもらうよう、要約に書く。検索結果の要約しか確認できないもの、WebFetch が開けず本文を照合できないものは、記事に書かない（「検索結果の要約」と明記して載せることもしない。人の方針 2026-10-12）。照合できる範囲は、e-Stat の API と確認済みの体験が中心になる。それでも具体が2件未満なら、そのテーマは別のテーマに替える（一般論で埋めない）。e-Stat の数字は、読み手の疑問と因果を説明できるときだけ使う。

## 前回の PR が未マージのまま次の実行になったとき（2026-10-12 追加）
- `seo/daily` に前回分（大量の底上げなど）が残っているときは、その上に積む。**PR の説明は、今日の分を冒頭に足し、前回までの確認用リンクを消さずに残す**（人は1つの PR でまとめて確認する）。
- 前回の底上げで `updated` を「翌日の日付」にしてある記事は、マージが遅れたら、マージ予定日に合わせて更新日を直す（playbook 5-5）。

- **スマホで文字が窮屈でないか（playbook 5-3i）**：最終チェックのスクリーンショットでは、段落・箇条書き・番号つきリストの間隔と、太字の導入文のあとの続き方まで見る。詰まって見えたら、共通 CSS かHTML化で直す（記事の書き方だけで逃げない）。

## 月1回のコードの点検（人の方針 2026-10-29）
毎月21日以降の最初の実行で、新規記事1本に加えて行う。AI で作り足していくと、使わなくなった CSS・同じ指定の重ね書き・巨大なファイルがたまり、直したいときに直せなくなる（技術負債）。月に1回、**見た目を1pxも変えずに**片付け、あわせてインデックス登録の土台を点検する。

1. **数字を取る**：`python3 tools/code_health.py --record`（大きいファイルの行数、CSS の `!important`・同じセレクタの重ね書き・使われていないルールの数、seo_check のエラー・警告）。`docs/seo/code-health.md` に1行たまるので、前月より増えた項目から片付ける。
2. **使われていない CSS を消す**：`python3 tools/css_prune.py` で一覧を見て、`python3 tools/css_prune.py --apply` → `python3 tools/build.py`。
3. **重ね書きを1か所にまとめる**：前回の点検のあとに足された CSS で、同じセレクタを後ろで上書きしているもの・`!important` で押し切っているものは、元のルールを直してまとめる（一度に直すのは数か所まで）。
4. **見た目が変わっていないことを確かめる**：`node tools/check/site_check.js`（本番との見た目の比較）で、整理した分の差分が 0 であること。差分が出た整理は、原因が分からなければ取り消す（整理で見た目を変えない）。HTML（`pages/`）が変わったときは、`git diff` で変わったのが CSS の版番号（`?v=`）だけであることを確かめる。
5. **インデックス登録の土台を点検する**：seo_check の「孤立ページ」（どこからもリンクされていない）・robots.txt・内部用パス（`/pages/`・`/seo/`）の転送・sitemap・canonical・noindex・リンク切れ・転送先へのリンクを 0 にする。Search Console の「ページのインデックス登録」で、「重複」「代替ページ」「クロール済み - インデックス未登録」「見つかりませんでした（404）」「リダイレクト」が増えていないかを見る（取れなければ、人に画面の確認を頼む項目として PR に書く）。
6. **大きな整理は提案だけ**：`tools/build.py` の分割など、ファイルの構成を変える整理は、その日の PR に入れず、週次レポートの「サイト全体の改修提案」に書く。
7. PR の説明に「コードの点検」の節を作り、数字（前月比）・整理したこと・見た目の差分 0 の確認結果を書く（マージは人）。

## 既存記事の「読みやすさの書き直し」（人の方針 2026-10-30）
新規記事で「点数を取るための文章に見えて読みにくい」「直訳調」「主語・目的語が抜けている」という指摘があった。既存の全記事も同じ可能性があるため、**水曜の底上げ枠で、1回5〜8本ずつ、順に書き直す**（新規記事1本は削らない）。
- **順番**：GA4/Search Console（`python3 tools/analytics.py`）で閲覧・表示の多い記事から。データが取れないときは `docs/seo/log.md` の「次回への引き継ぎ」の進み具合の続きから、公開日の新しい順。
- **直すこと（見せ方・言い回しだけ）**：やさしい言葉・1文40字前後、主語・目的語・述語をそろえる、直訳調（無生物主語・「〜することが重要です」・指示語と受け身の多用）をやめる、動詞を作業に合った言葉にする、断り書き・「と考えます」の反復・同じ数字の繰り返しを減らす、ポイントを本文を読まなくても分かる形にする、各節を前の節とつなぐ、題を専門語でなく読み手の悩み起点に（題を変えるときは旧URLは変えない）。基準は `.claude/agents/writer.md` 末尾・`docs/brand/voice.md`。
- **変えないこと**：事実・数値・出典・体験・主張・URL・公開日。
- **品質管理部**が、文法・直訳調・つながり・ポイントの意味が通るかを採点（90点以上・E-E-A-T の判定つき）。`seo_check`・`site_check`（スマホ幅の目視を含む）を通す。**見せ方だけの書き直しは、CLAUDE.md のとおり自分でマージしてよい**（ただし SEO の定期実行の PR は人を通す）。
- 進み具合は `docs/seo/log.md` に、書き直した記事のスラッグを残す。

## 週次レポートの「サイト全体の改修提案」（人の方針 2026-10-15）
- 計画（シミュレーション）に対して遅れているときは、課題を特定して、改善策を自分で実行しながらレポートに書く（記事の問題だけでなく、**サイト全体の構造・導線・計測・技術・デザイン**も見る）。
- サイト全体で直したほうがよい観点があれば、**容赦なく提案**として、週次レポートの「サイト全体の改修提案（人の確認が必要）」に書く。各提案に、①何が問題か（データか観察）②直し方 ③期待する効果と見る指標 ④工数 を1〜2行で付ける。
- **サイト全体の改修は大きいので、実行はマージ前に必ず人が確認する。** 提案だけを書き、勝手に大きな改修を入れない（小さな不具合の修正は従来どおり実行してよい）。
- 提案がないときは、無理に出さない（欄ごと省く）。
- 提案の元になるデータ（検索の表示・クリック、インデックス数、離脱、CV、AI引用）が取れない週は、「計測が取れていない」こと自体を最優先の提案にする。
